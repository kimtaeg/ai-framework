1

렌더는 사진이다: UI = f(state)

핵심 질문클릭 핸들러 안에서 setCount(count + 1) 을 세 번 부르면 왜 1 만 오를까? 2초 뒤에 count 를 읽으면 왜 옛날 값일까?
직관컴포넌트 함수가 한 번 실행될 때마다 그 순간의 state 로 찍은 사진 한 장이 나옵니다. 그 렌더 안에서 만든 이벤트 핸들러와 타이머도 같은 사진 속에 들어 있어요. 사진 속 숫자는 나중에 바뀌지 않습니다.

원리

count 는 변수가 아니라 상수입니다. const [count, setCount] = useState(0) 는 렌더마다 새로 실행되고, 그때마다 새 count 상수가 생깁니다. 핸들러는 자기가 태어난 렌더의 count 를 클로저로 붙잡고 있어요.

// 렌더 #1 (count = 0) 에서 만들어진 핸들러
onClick = () => {
  setCount(0 + 1);   // count 는 이 렌더에서 영원히 0
  setCount(0 + 1);
  setCount(0 + 1);   // → 결과 1
};
// 함수형 업데이트는 "그때의 사진" 대신 "가장 최신 값"을 받는다
setCount(c => c + 1); // ×3 → 결과 3

이 모델이 주는 이점은 예측 가능성입니다. 한 렌더 안의 값은 어디서 읽어도 같고, 중간에 누가 바꾸지 않습니다. 반대로 "최신 값"이 꼭 필요하면 렌더와 상관없이 유지되는 상자, useRef 를 씁니다.

실험 1 2초 뒤에 무엇이 보일까?

예측: "2초 뒤 state 읽기"를 누르고 바로 +1 을 세 번 누르면, 기록에 어떤 숫자가 찍힐까요? ref 버전은요?

더 깊이: 왜 React 는 state 를 "그냥 변수"로 만들지 않았을까?

변수(가변 객체)로 만들면 this.state.count 처럼 언제 읽느냐에 따라 값이 달라집니다. 클래스 컴포넌트가 실제로 그랬고, "저장 버튼을 누르고 3초 안에 다른 사람 프로필로 넘어가면 엉뚱한 사람 이름으로 알림이 뜨는" 버그가 대표적이었습니다(this.props 가 바뀌어 버림).

함수 + 상수 모델에서는 한 번의 렌더가 하나의 일관된 세계입니다. 그래서 React 가 렌더를 버리거나 다시 해도(동시성 렌더링) 결과가 꼬이지 않습니다. 사진은 몇 번 다시 찍어도 안전하니까요.

생각 실험: 렌더 함수 안에서 Math.random() 을 쓰면 어떤 문제가 생길까?
같은 state 인데 렌더할 때마다 다른 화면이 나옵니다. "UI = f(state)" 가 깨져서, 관계없는 리렌더만으로 화면이 바뀌고 diff 도 매번 변경을 만듭니다. 무작위 값이 필요하면 useState(() => Math.random()) 처럼 처음 한 번만 만들어 저장합니다. StrictMode 가 개발 중에 렌더를 일부러 두 번 하는 것도 이런 비순수 코드를 찾기 위해서입니다.
내 코드에서 src/lib/component.js 의 useState: 렌더마다 [hook.value, hook.setState] 를 돌려줍니다. setState 는 함수가 들어오면 action(slot.value) 로 최신 값을 넘깁니다.
2

재조정의 두 가지 가정

핵심 질문두 트리의 "진짜 최소 차이"를 구하지 않고, 왜 일부러 덜 똑똑한 방법을 쓸까?
직관두 장의 그림에서 다른 곳을 찾을 때, 모든 조각을 모든 조각과 비교하면 끝이 안 납니다. 그래서 "같은 자리끼리만 비교하고, 종류가 다르면 통째로 새로 그린다"는 규칙을 정합니다. 가끔 손해를 보지만 언제나 빠릅니다.

원리

일반적인 트리 편집 거리(어떤 노드를 어디로 옮기고 지우고 넣을지의 최솟값)는 노드가 n 개일 때 O(n³) 이 걸리는 것으로 알려져 있습니다. 노드 1,000개면 10억 번입니다. React 는 두 가지 가정을 세워 O(n) 으로 줄였습니다.

가정 ① 타입이 다르면 다른 트리

<div> 가 <section> 이 되면 자식이 똑같아도 비교하지 않고 통째로 교체(REPLACE)합니다. 실제 앱에서 타입이 바뀌는데 자식이 그대로인 경우는 드물다는 관찰에서 나온 규칙입니다.

가정 ② key 가 같으면 같은 항목

형제끼리는 key 로 짝을 지어 "이동"을 알아냅니다. key 가 없으면 같은 위치끼리 비교합니다. 다른 부모로 옮겨 간 노드는 찾지 않습니다(같은 층에서만 비교).

실험 2 n 이 커지면 얼마나 차이 날까?
일반 트리 비교 O(n³)
React 방식 O(n)
차이

1초에 10억 번 연산한다고 가정한 대략적인 값입니다.

더 깊이: 가정이 틀리는 경우는? 그때 무슨 일이 생길까?

예: 로그인 여부에 따라 <div class="card"> 와 <section class="card"> 를 번갈아 그리면, 안의 입력칸까지 매번 새로 만들어집니다. 화면은 맞지만 입력하던 글자, 포커스, 스크롤 위치가 날아갑니다. 가정은 "정확성"이 아니라 "효율"과 "상태 보존"에 영향을 줍니다.

해결법: 바깥 태그를 같게 유지하고 안쪽만 바꾸거나, 반대로 일부러 초기화하고 싶을 때는 key 를 바꿉니다(key={userId}). key 를 바꾸면 React 는 "다른 항목"으로 보고 새로 만듭니다 — 상태 초기화 스위치로 쓰는 기법입니다.

내 코드에서 src/lib/diff.js 의 diff() 첫 부분: type 이나 key 가 다르면 바로 REPLACE 를 만들고 아래로 내려가지 않습니다.
3

key 는 정체성이다

핵심 질문key 를 배열 index 로 주면 화면은 맞게 나오는데, 왜 "쓰면 안 된다"고 할까?
직관교실 자리 번호(index)로 학생을 부르는 것과 이름(id)으로 부르는 것의 차이입니다. 누군가 맨 앞자리에 새로 앉으면 자리 번호는 한 칸씩 밀리지만, 책상 위에 둔 필통(DOM 상태)은 그대로 자리에 남아 있어요. 그러면 필통 주인이 바뀝니다.

원리

diff 는 key 가 같으면 "같은 노드"로 보고 기존 DOM 을 재사용합니다. 재사용된 DOM 에는 React 가 관리하지 않는 상태가 붙어 있습니다: 입력칸에 친 글자, 포커스, 체크 상태, 스크롤, 재생 중인 영상, CSS 애니메이션. index key 에서 맨 앞에 추가하면:

  • index key: key 0,1,2 는 그대로 있고 key 3 만 새로 생김 → 각 줄의 글자만 바꾸고(TEXT) 마지막 줄을 추가. 입력칸 DOM 은 자리에 남음 → 메모가 다른 사람 옆으로 감.
  • id key: 새 id 하나가 생김 → 맨 앞에 한 줄만 추가(INSERT). 기존 줄은 손대지 않음 → 메모가 주인을 따라감.
실험 3 메모가 누구 옆으로 갈까?

해 보기: 각 사람 옆 메모칸에 그 사람 이름을 적고 → "맨 앞에 한 명 추가"를 누르세요. key 방식을 바꿔서(초기화 후) 다시 해 보세요.

아직 변경 없음
더 깊이: 그럼 index key 를 써도 되는 경우는?
① 리스트 순서가 절대 바뀌지 않고, ② 중간 추가/삭제가 없고, ③ 항목에 DOM 상태나 자식 상태가 없을 때입니다. 세 조건이 다 맞으면 index 도 안전합니다. 하지만 요구사항은 나중에 바뀌니 고유한 id 가 있으면 id 를 쓰는 게 기본입니다. Math.random() key 는 최악입니다 — 렌더마다 모든 항목이 "다른 사람"이 되어 전부 새로 만들어집니다.
생각 실험: 제어 컴포넌트(value={memo})였다면 버그가 보였을까?
메모 값이 state 에 있고 각 사람 객체에 들어 있다면, index key 여도 렌더할 때 올바른 값이 다시 들어가 겉보기 버그는 사라집니다. 대신 매번 모든 줄의 value 를 고치는 패치가 생기고, 포커스와 커서 위치 같은 진짜 DOM 상태는 여전히 엉뚱한 줄에 남습니다. "상태를 어디에 두느냐"와 "정체성을 어떻게 정하느냐"는 별개의 문제입니다.
내 코드에서 diffChildren() 1단계: 이전 자식들을 key → 위치 Map 으로 만들고, 새 자식의 key 로 짝을 찾습니다. key 가 없는 자식끼리는 나온 순서대로 짝을 짓습니다.
4

최소 이동은 왜 LIS 인가

핵심 질문순서가 바뀐 리스트에서 "가만히 둬도 되는 항목"은 어떻게 고를까?
직관책장에서 책 순서를 바꿀 때, 이미 올바른 순서로 꽂혀 있는 책들은 그대로 두고 나머지만 빼서 끼워 넣으면 됩니다. "그대로 둘 수 있는 가장 많은 책"을 찾는 문제가 최장 증가 부분 수열(LIS)입니다.

원리

  1. 새 순서의 각 항목에 "이전 위치"를 적습니다. 예: 이전 A B C D E → 새 B C D E A 이면 [1, 2, 3, 4, 0].
  2. 이 수열에서 증가하는 가장 긴 부분 수열을 찾습니다: [1,2,3,4] = B C D E. 이 노드들은 서로의 상대 순서가 이미 맞으므로 움직이지 않습니다.
  3. 나머지(A)만 옮깁니다 → MOVE 1번. 위치가 바뀐 것을 전부 옮기는 방법이면 5번입니다.

LIS 는 이진 탐색으로 O(n log n) 에 구할 수 있습니다. 실제 React 는 비용을 더 줄이려고 "왼쪽에서 오른쪽으로 한 번 훑으며 마지막으로 놓은 위치보다 앞에 있던 것만 옮기는" 단순한 방법을 써서, 맨 끝 항목을 맨 앞으로 옮기는 경우 등에서 더 많이 움직입니다. Vue 3 와 Inferno 가 LIS 를 씁니다.

더 깊이: 이동 횟수를 줄이는 게 왜 중요할까? DOM 을 옮기는 건 빠르지 않나?
노드 하나를 옮기는 것 자체는 빠릅니다. 문제는 부작용입니다. DOM 에서 빠졌다 들어가는 순간 iframe 은 다시 로드되고, 영상은 멈추고, 포커스와 선택 영역이 사라지고, CSS 전환 효과가 다시 시작될 수 있습니다. 적게 옮길수록 사용자가 보는 상태가 덜 깨집니다. 그리고 레이아웃 계산(Reflow)도 덜 일어납니다.

5

Hook 은 왜 순서로 기억할까

핵심 질문useState(0) 에는 이름이 없는데, React 는 어떻게 "이게 아까 그 count 다"를 알까?
직관사물함에 이름표가 없고 번호만 있다고 생각해 보세요. 매일 같은 순서로 1번, 2번, 3번 칸을 열면 늘 자기 물건이 나옵니다. 어느 날 1번 다음에 갑자기 다른 칸을 하나 더 열면, 그 뒤로는 전부 남의 물건을 꺼내게 됩니다.

원리

컴포넌트마다 hooks 배열이 있고, 렌더 시작 때 hookIndex = 0 으로 돌립니다. Hook 을 부를 때마다 hooks[hookIndex++] 칸을 씁니다. 즉 호출 순서 = 이름입니다.

왜 이름(key)을 붙이는 설계를 안 했을까?

대안 설계문제
useState('count', 0) 처럼 이름 붙이기커스텀 Hook 을 두 번 쓰면 안쪽 이름이 충돌합니다. useWindowSize() 를 두 컴포넌트가 아니라 한 컴포넌트에서 두 번 쓰기만 해도 깨집니다.
Symbol 로 고유 키 만들기키를 컴포넌트 밖에 미리 만들어 둬야 해서 번거롭고, 같은 커스텀 Hook 을 두 번 부르는 문제는 그대로입니다.
클래스의 this.state로직(구독 + 해제)이 생명주기 메서드 여러 곳에 흩어지고, 재사용하려면 HOC/render props 로 감싸야 했습니다.
호출 순서 (채택)규칙 하나(조건문/반복문 안에서 부르지 않기)만 지키면 이름 충돌이 없고, 커스텀 Hook 이 그냥 함수 호출로 합성됩니다. 대가는 그 규칙 자체입니다.
실험 5 조건문 안의 Hook 이 칸을 밀어내는 순간

"메모 칸 켜기"를 누르면 1번 칸에 원래 useState:n 이 있어야 하는데 useRef 가 들어오려 합니다. miniReact 는 칸의 종류가 다르면 에러를 내고 마지막 화면을 그대로 둡니다.

더 깊이: 실제 React 는 배열이 아니라 연결 리스트를 쓴다는데, 무엇이 다를까?
React 는 Fiber 노드의 memoizedState 에 Hook 객체를 next 로 이어 붙입니다. 순서대로 따라가는 건 배열과 똑같아서 "순서가 곧 이름"이라는 원리는 같습니다. 연결 리스트를 쓰는 이유는 렌더 도중 작업 중인 트리(work-in-progress)와 화면에 있는 트리(current)를 따로 들고 있다가, 커밋 때 포인터만 바꿔 끼우기 쉽게 하려는 구현상의 선택입니다.
생각 실험: 그럼 반복문 안에서 Hook 을 부르면 왜 안 될까? 반복 횟수가 항상 같다면?
횟수가 정말 절대 안 바뀌면 동작은 합니다. 하지만 리스트 길이처럼 데이터에 따라 바뀌는 순간 칸이 밀립니다. 그래서 규칙은 "바뀔 수 있으면 금지"가 아니라 "항상 금지"입니다. 항목마다 상태가 필요하면 상태를 객체/배열 하나로 묶거나, 실제 React 에서는 항목을 별도 컴포넌트로 빼서 각자 Hook 을 갖게 합니다.
내 코드에서 getHookSlot(): 칸의 kind 가 다르면 "Hook 호출 순서가 바뀌었습니다", render() 끝에서 개수가 다르면 "Hook 호출 개수가 달라졌습니다" 에러를 냅니다.
6

Batching 과 이벤트 루프

핵심 질문setState 를 부르면 화면은 정확히 "언제" 바뀔까? useEffect 는 그보다 앞일까 뒤일까?
직관식당 주문을 생각해 보세요. 손님이 "물이요, 수저요, 앞접시요"를 연달아 말하면 직원은 한 번에 모아서 가져옵니다. 지금 하던 말(동기 코드)이 끝난 직후가 "모아서 처리하는" 시점입니다.

원리: 브라우저의 작업 줄

  1. 콜 스택 (동기 코드) 지금 실행 중인 함수. 끝날 때까지 아무도 끼어들 수 없습니다.
  2. 마이크로태스크 큐 Promise.then, queueMicrotask. 콜 스택이 비는 즉시, 화면을 그리기 전에 전부 비웁니다. miniReact 의 리렌더 예약이 여기 들어갑니다.
  3. 렌더링 (그리기) 브라우저가 필요하면 스타일 계산 → 레이아웃 → 페인트. requestAnimationFrame 콜백은 그 직전.
  4. 태스크(매크로태스크) 큐 setTimeout, 클릭 같은 이벤트. 한 번에 하나씩, 사이사이에 마이크로태스크와 그리기가 끼어듭니다.

그래서 마이크로태스크로 렌더를 예약하면 ① 같은 이벤트 안의 setState 는 전부 한 번에 모이고 ② 사용자는 중간 상태를 절대 보지 못합니다(그리기 전에 끝나니까). useEffect 는 반대로 그린 뒤로 미뤄서 화면 표시를 막지 않습니다.

실험 6 실행 순서 맞히기

아래 코드가 실행될 때 일이 일어나는 순서대로 카드를 누르세요. 다 고르면 실제로 실행해서 채점합니다.

setTimeout(() => log('setTimeout 0'), 0);
Promise.resolve().then(() => log('Promise.then'));
setN(v => v + 1);   // miniReact: 리렌더 → useLayoutEffect → (그린 뒤) useEffect
log('동기 코드 끝');
더 깊이: 렌더 예약을 setTimeout 으로 했다면 무엇이 달라질까?
setTimeout 은 태스크라서 그 사이에 브라우저가 먼저 그릴 수 있습니다. 그러면 사용자가 바뀌기 전 화면을 한 프레임 더 보거나, 이벤트 핸들러 두 개가 따로 렌더를 일으킬 수 있습니다. 반대로 마이크로태스크는 너무 많이 쌓이면 그리기 자체를 막습니다 — effect 안에서 setState 가 끝없이 이어지면 화면이 멈추는 이유이고, miniReact 가 중첩 업데이트 횟수를 세서 막는 이유입니다.
생각 실험: React 18 의 "자동 배칭"은 무엇을 바꿨을까?
React 17 까지는 React 이벤트 핸들러 안에서만 모아 처리했고, setTimeout 이나 fetch().then 안의 setState 는 부를 때마다 바로 렌더했습니다. React 18 부터는 어디서 부르든 모읍니다. miniReact 는 처음부터 "어디서든 마이크로태스크 하나로" 모으는 방식이라 18 과 비슷합니다. 즉시 반영이 꼭 필요하면 React 는 flushSync, miniReact 는 comp.flush() 를 씁니다.
내 코드에서 scheduleUpdate() 의 updateScheduled 플래그 + scheduleMicrotask, commit() 의 afterPaint (requestAnimationFrame → setTimeout).
7

Effect 는 생명주기가 아니라 동기화다

핵심 질문useEffect 를 "마운트될 때 실행"으로 이해하면 어디서 틀릴까?
직관에어컨 온도 조절기를 떠올리세요. "켜질 때 한 번 맞추는" 게 아니라, 설정 온도(의존성)가 바뀔 때마다 실제 온도를 거기에 맞추고, 이전 설정은 정리합니다. Effect 는 "React 밖 세상(서버, 타이머, 구독)을 지금 state 에 맞추는 장치"입니다.

원리

질문을 "언제 실행되지?"에서 "무엇과 무엇을 맞추지?"로 바꾸면 의존성 배열이 저절로 정해집니다. effect 가 읽는 값은 모두 의존성입니다. 그리고 cleanup 은 "언마운트 때"가 아니라 "다음 동기화 직전마다" 실행됩니다.

useEffect(() => {
  let ignore = false;           // 이 동기화가 아직 유효한가?
  fetch(`/search?q=${query}`).then(r => {
    if (!ignore) setResult(r);  // 낡은 동기화의 결과는 버린다
  });
  return () => { ignore = true; }; // query 가 바뀌면 이전 동기화를 무효로
}, [query]);

응답은 보낸 순서대로 오지 않습니다. "re" 요청이 1.3초, "react" 요청이 0.2초 걸리면 늦게 온 "re" 결과가 "react" 결과를 덮어씁니다. 이것이 경쟁 상태(race condition)입니다.

실험 7 늦게 온 응답이 최신 결과를 덮어쓴다

응답마다 걸리는 시간은 0.2~1.5초 사이 무작위입니다. 체크를 끈 채로 "자동 타이핑"을 몇 번 눌러 보고, 켠 채로 다시 해 보세요.

더 깊이: 의존성 배열에서 값을 빼면 "최적화"일까?
아닙니다. 의존성 배열은 "언제 실행할지 고르는 옵션"이 아니라 "이 effect 가 무엇을 읽는지에 대한 사실"입니다. 읽는 값을 빼면 effect 는 옛날 사진(1번 주제의 클로저)을 계속 보게 됩니다. 실행을 줄이고 싶으면 의존성을 빼지 말고 effect 가 그 값을 읽지 않게 코드를 바꿔야 합니다(함수형 업데이트, useReducer, 값을 effect 안으로 옮기기 등).
생각 실험: 이 effect 는 정말 필요할까?
"props 로 받은 목록을 필터링해서 state 에 저장하는 effect" 는 필요 없습니다 — 렌더 중에 계산하면 됩니다(필요하면 useMemo). "버튼을 눌렀을 때 서버에 보내기" 도 effect 가 아니라 이벤트 핸들러의 일입니다. effect 는 화면에 보이는 것 때문에 외부와 맞춰야 할 때만 씁니다. 불필요한 effect 는 렌더를 한 번 더 일으키고 상태를 두 군데에 둡니다.
내 코드에서 effectHook() 가 depsChanged 로 이전 deps 와 Object.is 비교, flushPassiveEffects() 가 "모든 cleanup 먼저, 그다음 모든 effect" 순서로 실행합니다.
8

불변성과 Object.is

핵심 질문배열에 push 하고 setState 했는데 왜 화면이 안 바뀔까? 왜 React 는 내용을 깊이 비교해 주지 않을까?
직관택배 상자 바꿔치기 검사를 생각해 보세요. 상자 번호(참조)만 보면 1초면 끝나지만, 상자를 열어 내용물을 하나하나 비교하면 오래 걸립니다. React 는 번호만 봅니다. 그러니 내용을 바꿨다면 새 상자에 담아야 바뀐 걸 압니다.

원리

setState, 의존성 배열, memo 는 모두 Object.is(이전, 다음) 으로 비교합니다. 숫자·문자열은 값으로, 객체·배열은 참조(주소)로 비교합니다. 원본을 고치면 주소가 같으니 "변화 없음"으로 판단해 렌더를 건너뜁니다.

깊은 비교를 하지 않는 이유

깊은 비교는 데이터 크기에 비례해 느리고, 순환 참조나 함수, Date 같은 특수 객체에서 애매합니다. 매 렌더마다 모든 state 와 props 를 깊게 비교하는 비용이 렌더 자체보다 클 수 있습니다.

불변성이 주는 것

"바뀌었나?"가 O(1) 비교가 됩니다. 이전 값이 그대로 남아 있어 실행 취소, 시간 여행 디버깅, 이전 ↔ 새 비교가 쉽습니다. 바뀌지 않은 부분은 참조를 공유하므로(구조 공유) 복사 비용도 생각보다 작습니다.

실험 8 같은 상자 vs 새 상자
메모리 속 배열에 실제로 들어 있는 개수: 1

push 버튼을 몇 번 누른 뒤 새 배열 버튼을 누르면, 그동안 몰래 들어간 항목이 한꺼번에 나타납니다. 화면과 데이터가 어긋나 있던 거예요.

더 깊이: 렌더마다 { } 나 () => {} 를 새로 만들면 왜 useMemo 가 무력해질까?
useMemo(fn, [options]) 에서 options = { sort: 'asc' } 를 렌더 안에서 만들면 내용은 같아도 렌더마다 새 주소입니다. Object.is 는 매번 false → 매번 다시 계산합니다. 해결: 원시값을 의존성으로 쓰거나([options.sort]), 객체 자체를 useMemo 로 고정하거나, 컴포넌트 밖으로 뺍니다. useCallback 이 존재하는 이유도 함수의 주소를 고정하기 위해서입니다.
내 코드에서 useState 의 if (Object.is(next, slot.value)) return; 한 줄이 이 실험의 전부입니다. depsChanged() 도 같은 비교를 씁니다.
9

멈출 수 있는 렌더링: Fiber 와 시간 쪼개기

핵심 질문diff 가 O(n) 으로 빠른데도 큰 화면에서 버벅이는 이유는? Fiber 는 그걸 어떻게 해결했을까?
직관설거지 100개를 한 번에 다 하는 동안 초인종이 울려도 못 나가는 것과, 5개씩 하고 잠깐 손을 닦으며 문 앞을 확인하는 것의 차이입니다. 전체 시간은 비슷하거나 조금 더 길지만, 손님(사용자 입력)은 기다리지 않습니다.

원리

브라우저는 1초에 약 60번(16.7ms 마다) 화면을 그리고 싶어 합니다. 그런데 자바스크립트가 실행되는 동안에는 그리기도, 클릭 처리도 못 합니다. 재귀로 트리 전체를 한 번에 비교하면 중간에 멈출 방법이 없습니다 — 콜 스택이 곧 진행 상태라서요.

Fiber 는 콜 스택 대신 노드마다 작업 단위를 객체로 만들어 child / sibling / return 포인터로 잇습니다. 진행 상태가 힙에 있으니 몇 ms 마다 "급한 일 있나?" 확인하고 양보했다가 이어서 할 수 있습니다. 더 급한 업데이트(타이핑)가 오면 하던 렌더를 버리고 새로 시작할 수도 있습니다 — 1번 주제의 "렌더는 사진"이라 버려도 안전합니다.

실험 9 공이 멈추는지 보세요

더 깊이: 그럼 miniReact 를 Fiber 로 바꾸려면 무엇을 고쳐야 할까?

① diff() 의 재귀를 "다음 작업 노드" 포인터를 따라가는 반복문으로 바꿉니다. ② 렌더 단계에서는 DOM 을 건드리지 않고 변경 목록만 쌓습니다(이미 그렇게 되어 있습니다 — patches 배열). ③ 작업 루프에서 시간을 재다가 5ms 가 넘으면 MessageChannel 등으로 양보합니다. ④ 모든 비교가 끝났을 때만 patches 를 한 번에 반영(커밋)합니다.

②번 덕분에 miniReact 도 "비교는 쪼개고, 반영은 한 번에" 구조로 갈 수 있는 바탕은 갖춘 셈입니다.

내 코드에서 update() 는 render → diff → applyPatches 를 한 번에 동기로 끝냅니다. 그래서 1,000행 리스트 예제에서 렌더 시간이 그대로 화면 멈춤이 됩니다.
10

Render 와 Commit 을 나눈 이유

핵심 질문계산하면서 바로바로 DOM 을 고치면 더 빠를 텐데, 왜 "계산 단계"와 "반영 단계"를 나눌까?
직관건축에서 설계도를 다 그린 뒤 공사를 시작하는 것과 같습니다. 설계는 몇 번을 고쳐도 아무도 다치지 않지만, 공사를 반쯤 하다 멈추면 반쯤 무너진 건물이 남습니다.

나누면 얻는 것

얻는 것왜
일관성사용자는 "반쯤 바뀐 화면"을 절대 보지 않습니다. 반영은 한 번에 동기로 끝나니까요.
중단·재시작계산 단계는 외부에 흔적을 남기지 않아서, 멈추거나 버리거나 다시 해도 됩니다(9번 주제).
측정 타이밍useLayoutEffect 는 "반영은 끝났고 아직 안 그린" 정확한 순간을 얻습니다. 크기를 재서 위치를 고쳐도 깜빡이지 않습니다.
디버깅·도구변경 목록(patches)이 데이터로 남으니 단계별로 보여 주거나, 몇 개가 바뀌었는지 셀 수 있습니다. 이 프로젝트의 Inspector 와 단계별 Patch 가 그 예입니다.

대가는 규칙입니다: 렌더 함수는 순수해야 합니다. 렌더 중에 DOM 을 고치거나 서버에 요청하면 "계산은 버려도 안전하다"는 전제가 깨집니다. 부수 효과는 이벤트 핸들러나 effect 로 보내야 하는 진짜 이유가 이것입니다.

더 깊이: 동시성 렌더링의 "tearing(찢어짐)"은 무엇일까?
렌더를 쪼개서 하는 도중에 React 밖의 저장소(전역 변수, 외부 상태 라이브러리)가 바뀌면, 화면의 앞부분은 옛 값, 뒷부분은 새 값으로 그려질 수 있습니다. 한 화면이 두 시점으로 찢어지는 거죠. React 18 은 이를 막으려고 useSyncExternalStore 를 만들어, 외부 저장소가 바뀌면 그 렌더를 동기로 다시 하게 했습니다. "렌더 한 번 = 한 시점의 사진" 원칙을 지키기 위한 장치입니다.
내 코드에서 update(): render() 와 diff() 는 DOM 을 안 건드리고, applyPatches() 만 DOM 을 바꾼 뒤 commit() 에서 layout effect 를 실행합니다.
11

Virtual DOM 은 정답일까: 다른 설계와 비교

핵심 질문"Virtual DOM 이 직접 DOM 조작보다 빠르다"는 말은 맞을까?
직관내비게이션이 길을 찾아 주는 건 편하지만, 길을 완벽히 아는 사람이 직접 운전하는 것보다 빠르지는 않습니다. Virtual DOM 은 "사람이 길을 몰라도 꽤 좋은 길로 가게 해 주는" 도구입니다.

원리

정확히 무엇이 바뀔지 아는 사람이 손으로 쓴 DOM 코드가 가장 빠릅니다. Virtual DOM 은 그 위에 "새 트리 만들기 + 비교"라는 비용을 더합니다. 얻는 것은 속도가 아니라, 선언형으로 써도 충분히 빠르다는 보장입니다. 그러면 "어디를 고쳐야 하지?"를 사람이 기억하지 않아도 됩니다.

방식바뀐 곳을 찾는 방법장점단점
직접 DOM 조작개발자가 기억가장 빠를 수 있음화면이 커지면 빠뜨리는 곳 = 버그
Virtual DOM (React, miniReact)실행할 때 두 트리 비교그냥 JS 함수라 유연함, 생태계바뀌지 않은 부분도 다시 계산·비교
세밀한 반응성 / Signals (Solid, Vue 반응성, Preact Signals)값을 읽은 곳을 기록해 두고 그곳만 갱신비교 없이 정확히 그 노드만구독 관리, 구조분해하면 반응성 끊김 등 규칙
컴파일러 (Svelte, React Compiler)빌드할 때 코드를 분석실행 비용이 적음빌드 단계 필요, 분석 못 하는 패턴
더 깊이: 그럼 왜 React 는 아직 Virtual DOM 을 쓸까?
UI 가 "그냥 값을 돌려주는 함수"라는 단순한 모델은 테스트하기 쉽고, 같은 컴포넌트를 브라우저·서버(SSR)·모바일(React Native)·터미널 등 다른 곳에 그릴 수 있게 합니다 — 비교 결과를 어디에 반영할지만 바꾸면 되니까요(렌더러 분리). 또 React Compiler 처럼 자동 메모이제이션으로 "바뀌지 않은 부분 다시 계산" 비용을 줄이는 방향으로 진화하고 있습니다.
생각 실험: 이 프로젝트의 "Virtual DOM vs 전체 다시 그리기" 비교에서 무엇을 확인할 수 있었나?
예제 페이지의 비교는 Virtual DOM 이 innerHTML 로 전체를 다시 만드는 방식보다 DOM 변경이 훨씬 적다는 것을 보여 줍니다. 하지만 "정확히 한 칸만 고치는 손 코드"와 비교한 게 아니라는 점에 주의하세요. 올바른 결론은 "Virtual DOM 은 선언형의 편의를 유지하면서 변경량을 직접 조작에 가깝게 줄인다"입니다.
12

miniReact 의 한계를 스스로 찾아보기

핵심 질문내 구현이 실제 React 와 다른 곳은 어디이고, 그 차이는 어떤 상황에서 드러날까?

한계를 정확히 아는 것도 이해의 일부입니다. 아래 상황마다 "miniReact 에서는 무슨 일이 생길까?"를 먼저 답해 보고 펼쳐 보세요. 발표 질문 대비로도 좋습니다.

상황 1. 자식 컴포넌트 안에 체크박스 열림 상태를 두고 싶다면?
miniReact 는 Hook 을 루트에서만 허용하니, 상태를 루트로 끌어올려 props 로 내려야 합니다(Lifting State Up). 항목이 많아지면 루트 state 가 커지고, 항목 하나가 바뀌어도 루트 전체를 다시 렌더합니다. 실제 React 는 컴포넌트마다 Fiber 가 있어서 각자 Hook 을 갖고, 바뀐 컴포넌트 아래만 다시 렌더합니다. 과제 조건이 만든 의도적인 한계입니다.
상황 2. 10,000행 표에서 글자 하나를 고치면?
루트 함수를 다시 실행해 10,000행의 VNode 를 다시 만들고 전체를 비교합니다. DOM 변경은 1개지만 계산은 10,000행입니다. 완화책: 행 목록을 useMemo 로 기억하면 같은 참조라 diff 가 통째로 건너뜁니다(예제의 1,000행 리스트에서 확인 가능). 근본적으로는 컴포넌트 단위 렌더(상황 1)나 가상 스크롤(보이는 행만 그리기)이 필요합니다.
상황 3. 이벤트 핸들러를 1,000개 버튼에 각각 붙이면?
miniReact 는 요소마다 리스너를 하나씩 붙입니다(내부 프록시로 함수만 갈아끼움). React 는 루트 하나에만 리스너를 달고 이벤트가 버블링될 때 어느 컴포넌트의 핸들러인지 찾아 부릅니다(이벤트 위임). 리스너 수가 적어 메모리가 덜 들고, 동적으로 추가된 요소도 자동으로 처리됩니다.
상황 4. 렌더 도중 에러가 나면?
miniReact 는 safely() 로 잡아서 마지막으로 성공한 화면을 그대로 두고 onError 로 알립니다(실험 5 에서 본 동작). 실제 React 는 에러 경계(Error Boundary) 컴포넌트로 트리의 일부만 "대체 화면"으로 바꾸고, 경계가 없으면 트리 전체를 내립니다. 반쯤 망가진 화면을 보여 주는 것보다 낫다는 판단입니다.
상황 5. 서버에서 HTML 을 먼저 만들어 보내고 싶다면?
miniReact 에는 vnodeToHTML() 로 HTML 문자열을 만드는 기능은 있지만, 이미 있는 HTML 에 이벤트만 붙여 이어받는 Hydration 은 없습니다. mount 는 컨테이너를 통째로 새 DOM 으로 바꿉니다. Hydration 을 만들려면 createElement 대신 "기존 DOM 노드를 순서대로 짝지으며 이벤트만 붙이는" 함수가 필요합니다.
상황 6. 반대로 miniReact 가 React 보다 나은 점은?
리스트 재정렬에서 LIS 로 이동 횟수를 최소화합니다(4번 주제 — React 는 맨 뒤 항목을 맨 앞으로 옮기면 나머지를 전부 옮깁니다). 또 코드가 작아서 diff → patch → effect 의 모든 단계를 눈으로 따라갈 수 있습니다. 이것이 이 과제의 진짜 목적이기도 합니다.
