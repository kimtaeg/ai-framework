1. DOM 과 브라우저 API

DOM(Document Object Model) 은 HTML 문서를 브라우저가 메모리에 올린 객체 트리입니다. window 는 브라우저 창 전체(전역 객체, 타이머, 위치 정보 등)를, document 는 그 안의 문서(DOM 트리의 루트)를 가리킵니다.

  • 읽기: querySelector, childNodes, attributes, nodeType → domToVNode() 에서 사용
  • 쓰기: createElement, insertBefore, replaceChild, setAttribute, nodeValue → applyPatches() 에서 사용
  • 변화 감지: MutationObserver — DOM 에 일어난 변경(자식 추가/삭제, 속성, 텍스트)을 기록합니다. Phase 1 / 2 화면에서 patch 직후 takeRecords() 로 실제 변경 수를 세어 "정말 필요한 곳만 바뀌었는지" 검증합니다.

2. 실제 DOM 이 느린 이유 — Reflow / Repaint

브라우저 렌더링 파이프라인: DOM + CSSOM → Render Tree → Layout(Reflow) → Paint(Repaint) → Composite

  • Reflow: 크기·위치가 바뀌면 영향받는 요소들의 레이아웃을 다시 계산합니다. 부모·형제·자식까지 연쇄적으로 번질 수 있어 비쌉니다.
  • Repaint: 색·그림자처럼 레이아웃과 무관한 시각 속성이 바뀌면 픽셀을 다시 칠합니다.
  • DOM 노드는 수백 개의 속성을 가진 무거운 객체이고, JS ↔ 렌더링 엔진 경계를 넘나드는 호출 자체에도 비용이 있습니다.
  • offsetHeight 같은 값을 읽으면 브라우저가 대기 중인 레이아웃을 강제로 계산합니다 (Layout Thrashing).

그래서 "변경을 가벼운 JS 객체에서 먼저 계산하고, 실제 DOM 조작은 최소한으로 모아서" 하는 것이 Virtual DOM 의 목적입니다.

3. Virtual DOM

구조

// Element
{ type: 'li', props: { class: 'item' }, key: 'a', children: [ ... ] }
// Text
{ type: '#text', props: {}, key: null, children: [], text: 'hello' }
  • h(type, props, ...children) — JSX 가 변환되는 React.createElement 와 같은 역할
  • domToVNode(node) — 실제 DOM 을 읽어 VNode 로. 들여쓰기 공백·주석은 무시, <script>·on* 속성 제거(sanitize)
  • createElement(vnode) — VNode 로 실제 DOM 생성 (SVG 네임스페이스 지원)
  • vnodeToHTML(vnode) — 테스트 영역 표시용 직렬화. 다시 파싱해도 같은 VNode 가 나오도록(round-trip) 설계

필요한 이유

  • 선언적 UI: "상태가 X 면 화면은 Y" 만 기술하면, 무엇을 바꿀지는 diff 가 계산합니다.
  • 최소 변경: 바뀐 노드에만 DOM API 를 호출 → Reflow/Repaint 범위 최소화.
  • 스냅샷: VNode 는 불변 객체라 히스토리(뒤로가기/앞으로가기)에 그대로 저장할 수 있습니다.

4. Diff 알고리즘

두 트리를 완전히 비교하는 최적 알고리즘은 O(n³) 입니다. React 처럼 두 가지 가정을 두어 O(n) 에 가깝게 비교합니다.

  1. 타입(태그)이 다르면 하위 트리를 비교하지 않고 통째로 교체한다.
  2. 형제 리스트에서는 key 로 같은 노드를 식별한다.

최소 변경을 위한 5가지 핵심 케이스

케이스조건DOM 반영
INSERTold 없음, new 있음insertBefore(createElement(new))
REMOVEold 있음, new 없음removeChild
REPLACE태그 또는 key 가 다름replaceChild (하위 트리 재생성)
TEXT텍스트 노드 내용이 다름nodeValue = text
PROPS같은 태그, 속성이 다름setAttribute / removeAttribute, 이벤트·style·value 처리
MOVE (추가)같은 key 의 위치 변경기존 노드를 insertBefore 로 이동 (재생성 X)

자식 리스트 재조정 (diffChildren)

  1. 매칭: key 가 있으면 key 로, 없으면 key 없는 노드끼리 순서대로 짝짓기
  2. 삭제: 짝이 없는 old 노드를 뒤에서부터 REMOVE (인덱스가 밀리지 않게)
  3. 배치: 남은 노드의 새 인덱스 수열에서 LIS(최장 증가 부분 수열) 를 구합니다. LIS 에 속한 노드는 상대 순서가 이미 맞으므로 그대로 두고, 나머지만 MOVE/INSERT. 예) [a,b,c,d] → [b,c,d,a] 는 단순 비교로는 3번 이동이지만 LIS 덕분에 1번만 이동합니다.
  4. 재귀: 위치가 확정된 뒤 짝지어진 노드끼리 diff

같은 객체 참조(old === new)면 하위 비교를 건너뜁니다 → useMemo 로 VNode 를 재사용하면 diff 비용 0.

5. Patch — 실제 DOM 반영

각 패치는 path(루트로부터 childNodes 인덱스 배열)로 대상을 가리킵니다. diff 가 패치를 만드는 동안 형제 순서 변화를 시뮬레이션하므로, 배열을 앞에서부터 순서대로 적용하면 경로가 항상 유효합니다.

{ type: 'TEXT',  path: [0, 2, 1], text: '새 텍스트' }
{ type: 'MOVE',  path: [0, 2], from: 3, to: 0 }
{ type: 'PROPS', path: [1], changes: [{ name: 'class', value: 'on', oldValue: 'off' }] }
  • 이벤트 핸들러는 리스너를 한 번만 등록하고 핸들러 함수만 교체합니다 (매 렌더 add/removeEventListener 하지 않음).
  • value/checked 는 attribute 와 property 를 함께 갱신 → 입력 중인 input 의 포커스와 커서가 유지됩니다.
  • Phase 1 은 로드 시 실제 영역의 들여쓰기 공백·주석을 정리(normalizeDom)해 DOM 인덱스와 VNode 인덱스를 맞춥니다.

React 에서는?

React 는 Render 단계(컴포넌트 실행 → 새 Fiber 트리, 변경 표시)와 Commit 단계(표시된 변경을 한 번에 DOM 반영)로 나눕니다. 이 구현도 render()(순수 계산)와 applyPatches()(DOM 반영)를 분리했습니다.

6. Component — UI 를 어떻게 나눌까?

  • 한 가지 역할을 기준으로 나눕니다: 헤더(진행률), 입력 폼, 필터 툴바, 목록, 항목, 타이머, 배칭 데모.
  • State 는 루트(App)에만 둡니다. 여러 자식이 같은 데이터를 쓰기 때문에 가장 가까운 공통 부모로 끌어올립니다 (Lifting State Up).
  • 자식은 props → VNode 순수 함수입니다. 자식이 상태를 바꾸려면 부모가 내려준 콜백(onToggle 등)을 호출합니다. → 데이터는 위에서 아래로, 이벤트는 아래에서 위로.
  • 자식에서 Hook 을 호출하면 에러를 던져 제약을 강제합니다.
class FunctionComponent {
  hooks = [];          // 상태 저장소
  mount(container)     // render → createElement → 부착 → effect
  update()             // render → diff → applyPatches → effect
}

7. State 와 Hooks

"함수는 매번 새로 실행되는데, 상태는 어떻게 유지할까?"

상태를 함수 바깥, 컴포넌트 인스턴스의 hooks 배열에 저장합니다. 렌더 직전에 currentComponent = this; hookIndex = 0 으로 두고, Hook 이 호출될 때마다 hooks[hookIndex++] 슬롯을 꺼내 씁니다. 호출 순서가 곧 상태의 식별자이므로 조건문 안에서 Hook 을 부르면 안 됩니다. 이 구현은 순서·개수가 바뀌면 에러로 알려줍니다.

Hook슬롯에 저장동작
useState{ value, setState }lazy 초기값, 함수형 업데이트, 같은 값이면 리렌더 생략, setter 참조 고정
useEffect{ deps, cleanup }렌더 중엔 예약만 하고 커밋 후 실행. deps 변경 시 이전 cleanup → 새 effect. 언마운트 시 cleanup
useMemo{ value, deps }deps 가 같으면 이전 값 반환
+ useLayoutEffect{ deps, cleanup }DOM 반영 직후, 그리기 전에 동기 실행
+ createContext / useContext(슬롯 없음)Provider 값을 렌더 중 스택으로 전달. 상태를 만들지 않으므로 자식에서도 허용
+ useCallback, useRef, useReducer추가 구현

8. setState 는 무엇을 해야 할까? — Batching

  1. 새 값 계산 (함수면 이전 값을 넣어 호출)
  2. 이전 값과 같으면(Object.is) 아무것도 하지 않음
  3. 슬롯에 값 저장
  4. 리렌더 예약: 바로 렌더하지 않고 queueMicrotask 로 예약. 이미 예약돼 있으면 무시

그래서 한 이벤트 핸들러 안에서 setState 를 여러 번 호출해도 동기 코드가 끝난 뒤 한 번만 렌더링됩니다. Phase 2 의 "setState × 3" 버튼으로 확인할 수 있습니다.

setState→microtask 예약→render→diff→patch→effects

effect 안에서 setState 가 끝없이 반복되면 50회에서 멈추고 에러를 냅니다 (무한 루프 방지).

9. 실제 React 와의 차이점

항목miniReactReact
재조정 구조재귀 트리 비교, 한 번에 끝까지Fiber (연결 리스트). 작업을 쪼개 중단·재개 가능 (Concurrent)
상태 위치루트 컴포넌트만 (과제 제약)모든 컴포넌트가 각자 Fiber 에 hooks 연결 리스트 보유
스케줄링microtask 1개로 batchingLane 기반 우선순위 (transition, 사용자 입력 우선 등)
useEffect 시점화면 그린 뒤 실행 (rAF → 다음 작업), useLayoutEffect 는 DOM 반영 직후 동기페인트 이후 비동기 실행. 별도로 useLayoutEffect 제공
이벤트각 요소에 네이티브 리스너루트 하나에 위임하는 합성 이벤트 (SyntheticEvent)
리스트 이동LIS 로 최소 이동왼쪽→오른쪽 단일 패스 (lastPlacedIndex)
기타—JSX, Fragment, Suspense, 에러 경계, Portal, SSR/Hydration, React.memo (Context 는 miniReact 에도 구현)
