EXPERIMENT 1 · CLIENT VS SERVER TRUTH

"웹사이트를 F12로 고치고 새로고침하면 왜 원래대로 돌아올까?"

아래의 두 상자를 보세요. 왼쪽은 내 컴퓨터 브라우저의 화면(복사본)이고, 오른쪽은 은행 전산실의 DBMS 금고(진짜 원본)입니다.
F12로 화면 숫자를 고쳐보고, 새로고침을 눌러서 데이터가 어디서 어떻게 복원되는지 확인해 보세요.

💻 내 컴퓨터 브라우저 (리액트가 그린 화면) 임시 복사본 (휘발성)
카카오뱅크 통장 잔액
10,000원
* 서버에서 복사해 온 데이터입니다.
🏛️ 은행 서버 DBMS 금고 (NVMe SSD) 진짜 원본 (SSOT)
account 테이블 원본 행 (Row)
10,000원
* WAL 로그와 B+ Tree로 잠겨 있는 진짜 원본입니다.
💡 깨달음 포인트: [1단계]를 누르면 내 브라우저 화면의 글자는 10억 원으로 바뀌지만, 오른쪽 은행 금고(DBMS)의 진짜 원본은 1원도 바뀌지 않는 것을 확인할 수 있습니다. 이제 [2단계 새로고침]을 누르면 무슨 일이 일어나는지 확인해 보세요!

🎓 이 실험을 통해 반드시 이해해야 하는 핵심 원리

1. 클라이언트 비신뢰 원칙 (Never Trust Client)

브라우저(F12)에서 조작할 수 있는 모든 데이터는 신뢰할 수 없습니다. 따라서 결제 금액, 잔액, 할인율, 관리자 권한 검증은 절대로 리액트(프론트엔드) 화면에 맡겨선 안 되며, 오직 백엔드 서버와 DBMS에서만 최종 검증해야 합니다.

2. 단일 진실 원천 (Single Source of Truth, SSOT)

브라우저 화면은 '빔프로젝터 스크린(복사본)'에 불과하며, 데이터의 '필름 원판(진짜 원본)'은 오직 DBMS 금고에 있습니다. 새로고침(F5) 시 브라우저는 힙(Heap) 메모리를 비우고 서버의 진짜 금고에서 데이터를 다시 긁어오므로 원상복구됩니다.

🎙️ 면접 & 구술 디펜스 모범 답변: "F12로 DOM 텍스트 노드를 변조해도 이는 로컬 단말기 브라우저 탭 프로세스의 RAM 힙 영역만 고친 것에 불과하며, 원격 서버나 디스크에는 아무 패킷도 전달되지 않습니다. 새로고침 시 브라우저는 Page Unload 이벤트와 함께 메모리를 해제하고, 서버 DBMS의 단일 진실 원천(SSOT)으로부터 데이터를 재조회하므로 무결성이 보장된 원래 데이터로 복원됩니다."
EXPERIMENT 2 · POLYGLOT PERSISTENCE

"DBMS에 모든 정보를 다 넣으면 안 되는 이유"

아래에 등장하는 데이터 카드를 보고, 어느 저장소에 넣어야 시스템이 터지지 않고 안전할지 직접 선택해 보세요.
잘못 넣었을 때 컴퓨터 시스템에 어떤 참사가 일어나는지 즉시 피드백을 보여드립니다.

질문 1 / 4
"스마트폰 SMS로 도착한 '3분 유효기간 1회용 인증번호 (6자리)'"
이 데이터는 어디에 저장하는 것이 가장 현명할까요?

🎓 이 실험을 통해 반드시 이해해야 하는 핵심 원리

1. 버퍼 풀 오염 방지 (Buffer Pool Cache Pollution)

RDBMS는 디스크 읽기를 줄이기 위해 메모리에 '버퍼 풀'을 둡니다. 100MB 동영상 같은 큰 파일을 DB에 넣으면 버퍼 풀 메모리가 통째로 오염되어 계좌 테이블 같은 중요한 쿼리 속도가 10배 느려집니다. 동영상은 S3에 넣고 DB에는 URL 주소(문자열 50바이트)만 보관해야 합니다.

2. 데이터 수명 주기와 비용 분리 (RAM vs NVMe)

3분짜리 SMS 인증번호는 정전이 나도 복구될 필요가 없습니다. 이런 쓰레기 데이터를 무거운 NVMe SSD에 B+ Tree 인덱스를 쪼개가며 쓸 이유가 없습니다. 초단기 데이터는 Redis의 TTL(Time-To-Live) 메모리 만료로 자동 소멸시켜야 디스크 I/O가 낭비되지 않습니다.

🎙️ 면접 & 구술 디펜스 모범 답변: "모든 데이터를 한 DB에 넣는 것은 심각한 안티 패턴입니다. 데이터의 크기, 수명 주기, 트랜잭션 요구 수준(ACID)에 따라 저장소를 분리하는 '폴리글랏 퍼시스턴스'가 필수적입니다. 절대 손실되면 안 되는 핵심 장부만 RDBMS에 두고, 대용량 바이너리는 S3, 휘발성 임시 데이터는 Redis로 분리해야 DB 버퍼 풀 오염과 디스크 I/O 병목을 막을 수 있습니다."
EXPERIMENT 3 · RENDERING PERSPECTIVES

"렌더링 방식에 따라 구글 검색 로봇과 사람은 서로 다른 화면을 본다?"

CSR(리액트 기본형)과 SSR(서버 조리형) 버튼을 번갈아 눌러보세요.
"사람의 눈에 보이는 완성된 화면"과 "구글/네이버 검색 로봇이 읽어가는 실제 HTML 코드"가 어떻게 다른지 나란히 비교합니다.

👤 일반 사용자의 모니터에 보이는 화면 브라우저 화면
🤖 구글/네이버 검색 로봇이 읽는 HTML 소스 검색 엔진 시선 

          

        


        


        

          
🎓 이 실험을 통해 반드시 이해해야 하는 핵심 원리

          

            

              
1. 초기 HTML 페이로드(Payload)의 치명적 차이

              

                CSR은 서버가 빈 껍데기 <div id="root"></div>만 던져주고 브라우저가 JS를 돌려 화면을 그립니다. 반면 검색 로봇은 JS를 무겁게 실행하지 않고 첫 HTML 텍스트만 긁어가기 때문에 CSR은 빈 백지로 인식되어 검색 결과에서 누락됩니다.
              

            

            

              
2. 은총알은 없다 (No Silver Bullet / 트레이드오프)

              

                그렇다고 모든 페이지를 SSR로 만들면 서버 CPU가 매번 HTML을 조립하느라 서버 비용이 폭증합니다. 따라서 검색 노출이 생명인 쇼핑몰/뉴스는 SSR을 쓰고, 검색이 필요 없는 사내 어드민/노션은 가벼운 순수 CSR을 써야 합니다.
              

            

          

          

            🎙️ 면접 & 구술 디펜스 모범 답변:
            "CSR은 클라이언트가 번들 JS를 다운로드하고 실행(Hydration)한 뒤에야 DOM이 생성되므로, 초기 수신된 HTML 스트림만 인덱싱하는 검색 크롤러에게 빈 화면을 제공하는 구조적 한계(SEO 취약성)가 있습니다. 반면 SSR은 서버에서 완성된 HTML 텍스트를 스트리밍하므로 크롤러 색인과 첫 화면 표시(FCP)에 유리하지만, 서버 CPU 부하가 증가하므로 비즈니스 도메인에 맞게 기술을 선택해야 합니다."

🎓 이 실험을 통해 반드시 이해해야 하는 핵심 원리

          

            

              
1. 프론트엔드와 백엔드의 물리적 격리

2. 실제 파일 시스템 쓰기의 실체

          EXPERIMENT 5 · HYBRID ISLAND ARCHITECTURE
          
"형님의 아이디어 직접 구현: 중요한 부분만 SSR + 인터랙션만 CSR"

          

            "모든 걸 SSR로 하지 말고, 검색에 걸려야 하는 핵심 상품 정보만 서버에서 가볍게 조리하고(SSR),

            좋아요 버튼이나 팝업창 같은 건 브라우저에 외주(CSR)를 주면 비용도 아끼고 로딩도 빨라지지 않나?"

🎓 이 실험을 통해 반드시 이해해야 하는 핵심 원리

          

            

              
1. 컴포넌트 단위 분업 (RSC: React Server Components)

              

                과거에는 '페이지 전체'를 SSR로 할지 CSR로 할지 양자택일해야 했습니다. 하지만 최신 리액트는 컴포넌트 하나하나마다 역할을 분배합니다. 텍스트 정보는 서버에서 HTML로 0바이트로 만들어 내려주고, 클릭이 필요한 버튼만 브라우저 자바스크립트로 전송합니다.
              

            

            

              
2. 아일랜드 아키텍처 (Islands Architecture)

              

                웹페이지의 90% 이상은 사실 사용자가 클릭할 필요가 없는 순수 정적 글자(바다)입니다. 오직 찜하기 버튼이나 모달 창 같은 몇 군데만 자바스크립트가 동작하는 작고 독립된 섬(Island)으로 띄움으로써, 스마트폰 배터리와 메모리를 극적으로 아낄 수 있습니다.
              

            

          

          

            🎙️ 면접 & 구술 디펜스 모범 답변:
            "전통적인 SSR은 전체 페이지를 서버에서 직렬화하고 브라우저가 전체 트리를 재수화(Full Rehydration)하는 막대한 오버헤드가 있었습니다. 하지만 React Server Components(RSC) 기반의 하이브리드 분업을 적용하면, 검색 크롤러와 초기 사용자 경험에 필수적인 상품명·가격은 서버에서 0KB 번들로 완성(SSR)하고, 인터랙티브한 위젯만 선별적 클라이언트 컴포넌트('use client')로 격리함으로써 서버 연산 비용 절감과 클라이언트 번들 최적화를 동시에 달성할 수 있습니다."
