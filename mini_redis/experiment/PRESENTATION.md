## [0:40 ~ 1:25] 실험 구조와 통제

[화면: ② 첫 번째 다이어그램]

k6가 요청을 보내면 API 서버가 캐시를 먼저 보고, 없으면 미니 DBMS를 조회해 캐시에 넣습니다. 캐시는 **없음 · 미니 레디스 HTTP · 미니 레디스 RESP · Redis 7** 네 가지를 바꿔 끼웠고, Docker로 CPU 코어를 격리해 **96개 조건을 6번씩** 쟀습니다.

[화면: ③ "측정 중 발생한 오염과 해결" 표]

히트율은 응답 헤더로 실측했고, 반복마다 조건 순서를 섞었으며, 쓰기로 커진 테이블은 매번 **정확히 10만 건**으로 되돌렸습니다.

## [1:25 ~ 3:30] 핵심 결과 세 가지

[화면: ④ 맨 위 결과 표]

결과는 세 가지입니다.

[화면: 발견 1의 E2 그래프 → 표의 90% 줄]

**첫째, 무거운 쿼리는 공식대로 늡니다.**
DB로 가는 요청이 1 빼기 히트율만큼이라 처리량은 `DB 처리량 ÷ (1 - 히트율)`을 따르고, 히트율 **80%까지 오차 8% 이내**였습니다. 90%면 공식은 10배인데 실측은 **8.6배, 9.0배**였습니다. DB 처리량과 히트율만 알면 캐시 효과를 미리 계산할 수 있습니다.

[화면: 발견 2의 E3 표 → 요청당 CPU 표]

**둘째, 가벼운 쿼리에서는 캐시가 이기기 어렵습니다.**
B+ 트리 조회는 캐시 없이도 초당 **13,700건**이라, Redis도 히트율 **88%**를 넘어야 이득이고 미니 레디스 HTTP는 **100%여도 손해**였습니다.
같은 저장소를 통신만 RESP로 바꾸자 **6,800건에서 19,000건**이 됐고, 요청당 CPU도 **0.201밀리초에서 0.075밀리초**로 Redis와 같아졌습니다. 느린 원인은 저장소가 아니라 **HTTP와 JSON**이었습니다.

[화면: 발견 3의 E6 그래프 → ④ 맨 위 결과 표의 3번째 줄]

**셋째, 캐시까지 왕복 1ms가 생기면** 동시 요청이 많을 땐 처리량이 **8~22%**만 줄지만, 요청이 하나씩 오면 DB 조회 **0.39ms**보다 캐시 왕복이 비싸서 히트율 100%여도 **3.8배 느렸습니다.** 원본 쿼리가 네트워크 왕복보다 싸면, 캐시는 응답시간을 늘릴 뿐입니다.

[화면: 발견 3 아래 E7 한 줄]

다만 이건 캐시만 멀리 있는, 캐시에 가장 불리한 조건입니다. DB도 같이 멀리 두면 히트율 **96%**를 넘어야 약 **6%** 이득입니다.
