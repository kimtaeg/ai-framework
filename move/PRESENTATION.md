[화면: ② 프로파일 표]

[화면: ④ 코드 블록 — 예전 / 지금]

### 개선 2 · 숨은 n 제곱 (35초)

[화면: ⑤ complexity 그래프 — 두 선의 기울기]

목록 순서가 바뀔 때는 숨은 n 제곱이 있었습니다. 옮길 위치를 매번 배열을 처음부터 훑어 찾았기 때문인데, Pintos ready list 에 정렬 삽입을 n 번 하는 것과 같습니다. Fenwick 트리로 바꿔 5만 줄 뒤집기가 3초에서 23밀리초가 됐습니다.

★ [화면: ⑥ moves 그래프] 그리고 LIS 로 DOM 노드를 이론상 최소로만 옮깁니다. 1,000줄이면 999번 대 1번입니다.

# 1분 Q&A 방어 족보 — 핵심 4대 질문

답변 구조: **결론(5초) → 근거 · 수치(10초) → 한계 인정(5초)**

### Q1. LIS 는 다른 팀도 하는데, 뭐가 다른가요? (차별점)

> 저희 핵심은 LIS 가 아니라 diff 지연 자체입니다. 프로파일해 보니 시간의 60% 가 노드마다 만드는 작은 배열이었고, 이걸 없애 목록 재배치뿐 아니라 글자 하나 바뀌는 업데이트까지 모두 2배에서 3배 빨라졌습니다. LIS 쪽에서는 흔한 구현에 숨은 n 제곱을 찾아 고쳤습니다. 다만 Vue 같은 실제 라이브러리와 직접 시간을 비교하지는 않았습니다.

### Q2. 다른 컴퓨터나 모바일에서는 배수가 달라지지 않나요? (재현성)

> 절대 시간은 달라집니다. 하지만 노드 수만큼 생기던 할당을 없앤 것, n 제곱을 n log n 으로 바꾼 것은 구조의 차이라 경향은 같을 것으로 봅니다. 오히려 CPU 가 느린 모바일일수록 화면 시간에서 diff 가 차지하는 몫이 커져 효과가 클 수 있습니다. 다만 다른 기기에서는 아직 재 보지 않았습니다.

### Q3. 작은 배열 하나 만드는 게 왜 그렇게 비싼가요? (원리)

> 하나는 싸지만 노드 수만큼 매번 만듭니다. 1만 줄이면 다시 그릴 때마다 수만 개의 배열을 할당하고, 복사하고, 나중에 쓰레기 수집이 치워야 합니다. 함수 호출마다 malloc 과 free 를 하는 것과 같아서, 재귀 깊이만큼의 배열 하나를 재사용하게 바꿨습니다. 결과는 바꾸기 전과 4만 3천 건 대조해 같습니다.

### Q4. 그래서 화면은 얼마나 빨라지나요? (실용성)

> 1,000줄에서는 diff 가 1밀리초 정도라 diff 만 줄여서는 화면이 크게 달라지지 않습니다. 화면을 빠르게 한 건 DOM 을 덜 옮긴 쪽으로, 줄 하나를 위로 올릴 때 50밀리초가 24밀리초가 됐습니다. diff 개선은 노드가 많은 화면이나 느린 기기에서 더 드러납니다.

# 내가 짠 것처럼 말하기 — 핵심 원리 30초 멘탈 모델

> 1. **diff 지연 = 노드 수에 비례하는 일**
>    바뀐 게 한 글자여도 트리 전체를 훑습니다. 그래서 노드 하나당 하는 일이 조금만 무거워도 전체가 크게 느려집니다.
>
> 2. **할당 제거 = malloc 대신 스택 버퍼**
>    예전엔 자식마다 "루트에서 여기까지의 경로" 배열을 새로 만들었습니다. 이제는 재귀 깊이만큼의 배열 하나를 덮어쓰며 내려가고, 패치가 생길 때만 복사합니다. 바뀐 게 없으면 배열을 하나도 안 만듭니다.
>
> 3. **숨은 n 제곱 = 옮길 때마다 처음부터 세기**
>    LIS 는 누구를 옮길지만 알려 줍니다. 몇 번째 자리인지 찾으려고 매번 배열을 훑으면 n 제곱입니다. 1,000줄에선 안 보이고 5만 줄에서 3초가 됩니다.
>
> 4. **Fenwick 트리 = 앞부분 개수를 log n 에 세는 비트맵**
>    갈 자리를 미리 한 줄로 세우고 지금 DOM 에 있으면 1, 없으면 0. "내 앞에 1 이 몇 개?" 가 곧 인덱스입니다.

**외울 숫자 4개**: 할당 60% (프로파일) · 1만 줄 다시 그리기 38 → 12ms · 5만 줄 뒤집기 3초 → 23ms · 999 대 1
