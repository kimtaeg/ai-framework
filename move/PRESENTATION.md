## [0:00 ~ 0:40] 도입 — 문제

[화면: README ① 의 "key 없음 / key 있음" 표]

저희는 Virtual DOM 과 diff 를 직접 만들었습니다. 목록 순서가 바뀌면 diff 는 key 로 같은 줄을 찾고, 자리가 바뀐 줄을 실제 DOM 에서 옮깁니다. 이걸 MOVE 라고 부릅니다.

[화면: README ① 의 `a b c d → d a b c` 예시]

그런데 key 로 같은 줄을 찾은 다음, 어떤 줄을 옮길지 정하는 방법이 여러 가지입니다. 흔한 방법은 앞에서부터 보면서 순서가 어긋난 줄을 옮기는 겁니다. React 가 이 방식입니다. 이 방법은 맨 아래 줄 하나를 맨 위로 올리면, 나머지 줄이 전부 "앞으로 왔다" 고 판단해서 다 옮깁니다. 줄 하나 올리는데 세 번 옮기는 거죠.

## [0:40 ~ 1:20] 원리 — LIS

[화면: README ② 의 공식]

저희는 LIS, 최장 증가 부분 수열을 썼습니다. 새 순서대로 각 줄의 옛 위치를 적으면 3, 0, 1, 2 입니다. 여기서 커지는 순서로 이어진 0, 1, 2 는 서로 순서가 이미 맞으니까 그대로 두고, 3 하나만 옮깁니다.

남은 줄은 어떤 방법을 써도 한 번씩은 옮겨야 하니까, **남은 줄 수 빼기 LIS 길이가 이론상 최소**입니다. 저희 diff 는 항상 이 최소만큼만 옮깁니다.

★ Vue 3 와 같은 아이디어이고, 직접 구현해서 테스트로 최소인지 확인했습니다.

## [1:20 ~ 2:10] 시연

[화면: 비교 페이지 — 위쪽 두 패널]

왼쪽이 저희 diff, 오른쪽이 앞에서부터 방식입니다. 두 방식은 key 매칭, 패치 형식, DOM 에 적용하는 코드까지 전부 같고, 옮길 줄을 고르는 규칙 하나만 다릅니다.

[동작: "맨 아래 → 맨 위" 클릭]

채팅방 목록에 새 메시지가 온 방을 맨 위로 올리는 상황입니다. 번쩍이는 줄이 실제로 옮긴 줄입니다. 왼쪽은 한 줄, 오른쪽은 열한 줄이 번쩍입니다. 결과 순서는 똑같고, 적어 둔 입력칸 글자도 양쪽 다 제자리에 있습니다.

[화면: 페이지 "왜 이게 최소인가" — 초록 칸]

초록 칸이 LIS, 그대로 둔 줄입니다. 분홍 하나만 옮겼습니다.

## [2:10 ~ 3:10] 결과

[화면: README ④ 결과 1 표]

목록이 커지면 차이가 끝없이 커집니다. 1,000줄이면 999번 대 1번, 10만 줄이면 99,999번 대 1번입니다. 두 줄 바꾸기도 앞에서부터 방식은 그 사이를 전부 옮겨서 997번, 저희는 2번입니다.

[화면: README ④ 결과 2 표]

실제 브라우저에서 diff, patch, 레이아웃까지 재면 3.6배에서 8.2배 빨랐습니다. 옮기는 횟수만큼 빨라지지 않는 건, 두 방식이 똑같이 내는 계산과 레이아웃 비용이 있어서입니다.

[화면: README ④ 결과 3 표]

섞기나 뒤집기처럼 거의 다 움직이면 어떤 방법이든 n번 가까이 옮겨야 해서 이론상 차이가 날 수 없습니다. 처음엔 여기서 저희가 조금 느렸는데, 원인을 찾아 고쳐서 지금은 같은 속도입니다. 그래서 **어떤 경우에도 더 많이 옮기거나 더 느리지 않습니다.**

## [3:10 ~ 3:45] 직접 만든 최적화

[화면: README ⑤ 표]

LIS 를 쓰는 것에서 끝내지 않았습니다. 처음 구현은 옮길 위치를 찾을 때마다 배열을 뒤져서 O(n²) 이었고, 2만 줄을 뒤집는 데 0.8초가 걸렸습니다. 위치를 미리 좌표로 세우고 Fenwick 트리로 세게 바꿔서 21밀리초, 40배 빨라졌습니다.

★ 또 두 줄만 바뀐 경우의 빠른 길, 섞을 때 DOM 노드를 찾는 비용을 줄이는 묶음 처리도 넣었습니다. 바꾸기 전 코드와 무작위 4만 3천 건을 대조해서 결과가 하나도 다르지 않은 걸 확인했습니다.

## [3:45 ~ 4:00] 한계와 마무리

[화면: README ⑥ 한계 표]

★ 다만 key 를 아예 안 쓰고 글자만 고치는 방식과 비교하면, 전부 섞을 때는 노드를 옮기는 브라우저 비용 때문에 그쪽이 더 빠릅니다. 대신 입력하던 글자가 엉뚱한 줄로 밀립니다.

정리하면, 같은 결과를 **이론상 최소 횟수로** 만들고, 일부만 움직이는 흔한 경우에 수백 배 적게 옮기며, 어떤 경우에도 손해가 없다는 게 저희 diff 의 차별점입니다. 감사합니다.

# QnA 대비 — 20초 답변

답변 구조: **결론(5초) → 근거·수치(10초) → 한계 인정(5초)**

### Q1. React 는 왜 LIS 를 안 쓰나요? 그럼 React 가 틀린 건가요? (트레이드오프)

> 틀린 게 아니라 선택이 다릅니다. 앞에서부터 방식은 한 번 훑으면 끝나서 단순하고, 흔한 "맨 뒤에 추가" 나 "삭제" 는 LIS 와 똑같습니다. 차이는 줄을 앞으로 올리는 경우에 나고, 저희 측정에서 1,000줄 기준 999번 대 1번, 시간은 5.8배였습니다. 다만 저희 비교는 React 본체가 아니라 같은 규칙을 직접 구현해 같은 조건에서 잰 것입니다.

### Q2. LIS 계산 자체가 비싸지 않나요? (비용)

> LIS 는 O(n log n) 이라 1,000줄에서 1밀리초 안쪽입니다. 오히려 비쌌던 건 옮길 위치를 찾는 부분이었는데, 처음엔 O(n²) 이라 2만 줄 뒤집기에 0.8초가 걸렸고 Fenwick 트리로 바꿔 21밀리초가 됐습니다. 섞기처럼 다 움직이는 경우도 앞에서부터 방식과 같은 속도인 걸 확인했습니다.

### Q3. 실제 서비스에서 의미 있는 차이인가요? (실용성)

> 목록 하나를 위로 올리는 동작은 채팅방, 알림, 최근 항목처럼 아주 흔합니다. 2,000줄에서 65.8밀리초 대 18.4밀리초라서, 한 프레임(16밀리초)을 넘기느냐 마느냐의 차이입니다. 다만 노트북 한 대, Chrome 에서만 잰 결과이고, 수십 줄짜리 목록이면 둘 다 충분히 빠릅니다.
