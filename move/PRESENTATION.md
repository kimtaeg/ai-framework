# 1분 Q&A 방어 족보 — 핵심 4대 질문

답변 구조: **결론(5초) → 근거 · 수치(10초) → 한계 인정(5초)**

### Q1. LIS 는 Vue 3 도 쓰는데, 뭐가 다른가요? (차별점)

> 옮기는 횟수는 Vue 와 같은 이론상 최소입니다. 다른 건 그다음, 옮길 위치를 계산하는 부분입니다. 흔하게 짜면 n 제곱이라 5만 줄 뒤집기에 5초가 걸렸고, Fenwick 트리로 62밀리초가 됐습니다. 다만 Vue 본체와 직접 시간을 비교하지는 않았고, 비교 대상은 저희 최적화 전 코드입니다.

### Q2. 다른 컴퓨터에서 돌리면 배수가 완전히 달라지지 않나요? (재현성)

> 이동 횟수는 컴퓨터와 상관없이 똑같이 나옵니다. 순서만으로 정해지는 값이라서입니다. 시간의 절대값은 달라지지만, n 제곱 대 n log n 은 구조의 차이라 목록이 커질수록 벌어진다는 경향은 같습니다. 다만 1,000줄에서는 차이가 1.2배라 측정 흔들림과 비슷하고, 다른 컴퓨터에서는 아직 재 보지 않았습니다.

### Q3. 왜 하필 LIS 와 Fenwick 트리인가요? 다른 자료구조는요? (설계 근거)

> LIS 는 "이 이상 적게 옮길 수 없다" 를 증명할 수 있어서 골랐고, n log n 에 구해집니다. 위치 계산에 필요한 연산은 "한 칸을 켜고 끄기" 와 "앞부분 개수 세기" 두 가지뿐이라, 균형 트리보다 배열 하나로 되는 Fenwick 트리가 가장 단순했습니다. 연결 리스트로 들고 있으면 위치를 찾을 때 결국 처음부터 세야 해서 n 제곱으로 돌아갑니다.

### Q4. 실제 서비스 환경이라면 결과가 어땠을까요? (실용성)

> 실제 목록은 보통 수십에서 수백 줄이고, 긴 목록은 보이는 부분만 그리기 때문에 82배 같은 차이는 거의 나지 않습니다. 의미 있는 건 줄 하나를 위로 올리는 흔한 동작인데, 1,000줄에서 28밀리초 대 4.9밀리초라 한 프레임 16밀리초를 넘기느냐의 차이입니다. 남은 시간의 대부분은 안 바뀐 줄까지 비교하는 데 쓰여서, 다음 단계는 React 의 memo 처럼 그 비교를 건너뛰는 것입니다.

# 내가 짠 것처럼 말하기 — 핵심 원리 30초 멘탈 모델

> 1. **LIS = "이미 줄 선 사람은 그대로 둔다"**
>    새 순서대로 각 줄의 옛 위치를 적으면 수열이 됩니다. 그중 커지는 순서로 이어진 줄은 서로 순서가 맞으니 안 움직이고, 나머지만 한 번씩 옮깁니다. 그래서 "남은 줄 − LIS 길이" 가 최소입니다.
>
> 2. **숨은 n 제곱 = "옮길 때마다 처음부터 세기"**
>    LIS 는 누구를 옮길지만 알려 줍니다. 몇 번째 자리인지 찾으려고 매번 배열을 처음부터 훑으면, Pintos ready list 에 정렬 삽입을 n 번 하는 것처럼 n 제곱입니다. 1,000줄에선 안 보이고 5만 줄에서 5초가 됩니다.
>
> 3. **Fenwick 트리 = "앞부분 개수를 log n 에 세는 비트맵"**
>    모든 줄이 갈 자리를 미리 한 줄로 세우고, 지금 DOM 에 있으면 1, 없으면 0 으로 둡니다. "내 앞에 1 이 몇 개?" 가 곧 인덱스이고, Fenwick 트리는 이 합을 2의 거듭제곱 구간으로 나눠 미리 더해 두어 log n 에 답합니다.
>
> 4. **브라우저 캐시 무효화 = "TLB flush"**
>    `childNodes[i]` 는 내부에 위치 캐시가 있는데, DOM 을 바꾸면 버려집니다. 페이지 테이블을 바꾸면 TLB 를 비우는 것처럼, 이동이 많으면 매번 처음부터 찾게 됩니다. 그래서 이동이 이어지는 동안은 형제 목록을 JS 배열로 직접 들고 있습니다.

**외울 숫자 4개**: 999 대 1 (1,000줄 맨 위로) · 5,042ms → 62ms (5만 줄 뒤집기) · 1만 번 중 손해 0번 · LIS 는 전체의 2%
