해시 테이블 버킷 · 체이닝 · 점진적 리해시

위 콘솔과 같은 저장소입니다. 키 → FNV-1a 해시 → hash & (버킷 수 - 1) 로 버킷을 고르고, 같은 버킷이면 줄줄이 잇습니다(체이닝, 두 번째부터 주황색). 원소가 버킷 수보다 많아지면(부하율 > 1) 2배 테이블을 만들고 연산할 때마다 버킷 하나씩 옮깁니다(점진적 리해시).

관찰 포인트키를 4개 → 5개로 늘리는 순간 초록 테이블(새 테이블)이 생기고, 옛 테이블의 점선 버킷부터 하나씩 옮겨 갑니다. 옮기는 동안에도 GET 은 두 테이블을 모두 봐서 키를 놓치지 않아요. 한 번에 다 옮기면 100만 개일 때 서버가 그 순간 멈추기 때문에 이렇게 나눠서 옮깁니다.
만료 (TTL) 만료된 값을 요청받으면?

두 가지 방법을 함께 씁니다. 지연 삭제: GET 할 때 만료 시각을 확인해서 지났으면 그 자리에서 지우고 "없음"(nil)을 답합니다 → 만료된 값은 절대 나가지 않습니다. 주기 삭제: 100ms 마다 TTL 있는 키 20개를 무작위로 뽑아 만료된 것을 지우고, 25% 넘게 만료돼 있으면 한 번 더 → 아무도 안 읽는 키가 메모리를 차지하지 않게 합니다.

해 보기"주기 삭제 켜기"를 끄고 키를 만든 뒤 3초 기다리세요. 보이는 키는 10개로 줄지만 메모리에는 60개가 그대로 남아 있습니다(만료됐지만 남은 키). 이때 "전부 GET"을 누르면 지연 삭제가 한꺼번에 지웁니다. 다시 켜면 주기 삭제가 알아서 치웁니다.
캐시 API 응답 저장 · 무효화 · 성능 비교

cache-aside: ① 캐시에 있으면 바로 응답(HIT) ② 없으면 DB 에서 가져와(MISS) ③ 캐시에 저장(TTL 60초). 원본이 바뀌면 캐시의 그 키를 지웁니다(무효화) → 다음 요청이 새 값을 다시 캐시합니다.

동시성 GET + SET vs INCR

클라이언트 여러 명이 동시에 "좋아요 +1" 을 보냅니다. 요청마다 네트워크 시간이 달라서 도착 순서가 뒤섞입니다.

미니 레디스의 구조모든 명령은 한 스레드(이벤트 루프)에서 하나씩 실행되고, 명령 실행 코드(command())는 동기 함수라서 중간에 다른 요청이 끼어들 수 없습니다. 락이 없어도 명령 하나는 항상 원자적입니다. 여러 명령을 묶어야 하면 /pipeline 으로 한 번에 보내면 끼어들기 없이 실행됩니다. 실제 Redis 가 명령 처리를 한 스레드로 하는 이유도 같습니다.
영속성 (AOF) 서버가 다운돼도 데이터를 지키려면

쓰기 명령이 성공할 때마다 결과를 다시 만들 수 있는 명령을 파일 끝에 한 줄씩 덧붙입니다(Append Only File). 다시 켜면 처음부터 다시 실행해 복원합니다. TTL 은 "10초 뒤"가 아니라 "언제"(절대 시각)로 적어서, 꺼져 있던 동안 지난 시간도 반영됩니다.

해 보기everysec 에서 "주문 3건 쓰기"를 누르고 1초 안에 "서버 강제 종료"를 누르세요. 주황색(버퍼) 줄이 사라집니다. always 로 바꾸면 아무리 빨리 꺼도 잃지 않지만, 명령마다 디스크에 쓰느라 느립니다. 안전과 속도의 교환입니다. 실제 파일 저장은 week2/redis/persistence.js 이고, 테스트에서 실제로 프로세스를 죽였다 켜며 확인합니다.
