미니 레디스 한 장 요약

발표 직전에 훑어보는 핵심 정리. 인쇄하면 A4 한 장에 맞춰집니다.

① 요청 하나의 흐름

PUT /keys/k {value, ttl}
→ 입력 검사 (문자열, 1MB, ttl 정수)
→ command(['SET',k,v,'EX',ttl]) 동기 실행
→ fnv1a(k) & (size-1) → 버킷 → 체인
→ AOF: ["SET",k,v,"PXAT",시각]
→ 201 / 200

② 해시 테이블

  • 해시: FNV-1a (XOR + 소수 곱, 32bit)
  • 버킷 수 2ⁿ → hash & (m-1)
  • 충돌: 체이닝 (연결 리스트 맨 앞에)
  • 부하율 > 1 → 2배, < 0.1 → 축소
  • 평균 O(1), 최악 O(n)

③ 점진적 리해시

  • 테이블 2개 (옛 / 새)
  • 연산마다 옛 버킷 1개 이동
  • 조회·삭제: 둘 다 / 추가: 새 테이블만
  • 한 번에 옮기면 20만 개 중 131,072개를 한 연산이 / 나눠 옮기면 8개

④ 만료 (TTL)

  • 저장: 절대 시각 expireAt
  • 지연 삭제: 읽을 때 지났으면 삭제 + nil → 만료 값은 절대 안 나감
  • 주기 삭제: 100ms 마다 TTL 키 20개 표본, 25% 넘으면 반복 (최대 16번)
  • TTL: -2 키 없음, -1 만료 없음

⑤ 동시성

  • 한 스레드에서 동기 함수로 → 명령 하나는 원자적
  • GET → +1 → SET 은 원자적 아님 (lost update)
  • 해결: INCR, SET NX, pipeline
  • 약점: KEYS * 같은 긴 명령이 모두를 막음 → SCAN

⑥ 무효화

방법쓸 때
TTL"N초 옛 값 OK"
DEL원본 수정 직후 (덮어쓰기보다 안전)
TAG / INVALIDATE관련 키 한꺼번에
DELPATTERNproduct:*

⑦ 영속성 (AOF)

  • 쓰기마다 한 줄 JSON 덧붙임 → 재시작 때 재생
  • fsync: always(손실 0) / everysec(≤1초) / no
  • INCR 도 결과를 SET 으로 → 멱등
  • 잘린 마지막 줄은 버림
  • 재작성: 임시 파일 → fsync → rename

⑧ 캐시 (cache-aside)

GET 캐시 → HIT 면 끝
MISS → DB 조회 → SET 캐시 EX 60
원본 수정 → DEL 캐시
  • 없는 값도 짧게 캐시 (negative caching)
  • 스탬피드 → SET NX 로 한 명만 채우기

⑩ 예상 질문 한 줄 답

만료 값 요청?
읽을 때 확인해 삭제 + nil, 안 읽는 건 주기 삭제
동시성?
단일 스레드 · 동기 명령 → 명령 하나는 원자적
서버 다운?
AOF 재생, fsync 정책으로 손실량 선택
한계?
eviction · 복제 · 해시 씨앗 · SCAN 없음
테스트?
해시 퍼즈, 가짜 시계, 강제 종료 후 복원
