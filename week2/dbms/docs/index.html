세 단계(SQL 처리기 → B+ 트리 → API 서버)의 핵심 원리와 과제의 중점 포인트를 정리한 문서입니다.

1. 구조

cli.js / API→sql.js (토큰 → AST)→engine.js (계획 · 실행)→bptree.js→storage-file.js
  • Phase 1 — sql.js 토크나이저 + 재귀 하강 파서, engine.js 실행기, storage-file.js 테이블당 파일, cli.js
  • Phase 2 — bptree.js id → 위치 인덱스, 실행 계획(index-lookup / index-range / full-scan), seed.js · bench.js
  • Phase 3 — service.js 메인 스레드(파싱·락·분배), pool.js 스레드 풀, worker.js, lock.js

엔진은 저장소를 인터페이스(append / read / scan / flush)로만 써서 같은 처리기가 CLI(파일), 서버 워커(파일), 브라우저 실습(메모리)에서 그대로 돌아갑니다.

2. Phase 1 · SQL 처리기

토크나이저가 글자를 토큰(행/열 위치 포함)으로 자르고, 재귀 하강 파서가 문법 규칙 하나 = 함수 하나로 AST 를 만듭니다. 실행기는 AST 만 보고 저장소를 호출합니다.

SQL→토큰→AST→계획→실행→파일

지원: INSERT(여러 행, 열 생략) / SELECT(*, 열, WHERE =,!=,<,<=,>,>=,BETWEEN, AND, LIMIT), 주석, 여러 문장. 틀린 SQL 은 위치를 알려 줍니다: "'FROM' 이(가) 필요한데 'users' 이(가) 있습니다 (1행 10열)".

3. 파일 저장 방식

테이블 하나 = 파일 하나, 한 줄 = 레코드 하나. 쉼표·따옴표가 있으면 따옴표로 감싸고 NULL 은 \N, 줄바꿈은 \n. 레코드의 시작 바이트 위치만 알면 그 줄 하나만 읽을 수 있습니다. INSERT 는 1MB 씩 모아 쓰고, 여러 행 INSERT 는 전부 검사한 뒤에 쓰기 때문에 반만 저장되지 않습니다.

1,김정글,25,jungle@ex.com
2,"이, 리액트",30,\N

4. Phase 2 · B+ 트리 인덱스

INSERT 때 id 를 자동으로 부여하고 B+ 트리에 id → 레코드 위치를 등록합니다. 실행 계획기가 id 의 = 조건을 보면 트리에서 위치를 찾아 그 줄만 읽고, 범위 조건이면 리프 연결을 따라 범위만, 다른 열 조건이면 처음부터 끝까지 읽습니다.

100만 건시간
INSERT2.09초 (41.7MB, 높이 4)
id = ?0.038ms
email = ?1,032ms (약 27,000배)
재시작 인덱스 재구성0.47초

5. Phase 3 · API 서버와 동시성

메인 스레드가 요청을 받아 SQL 을 먼저 파싱해서(문법 오류는 바로 400) 읽는 테이블과 쓰는 테이블을 알아내고, 테이블별 읽기/쓰기 락을 이름 순서로 잡은 뒤 스레드 풀의 쉬는 워커에 맡깁니다.

요청→파싱→락→워커→인덱스 알림→락 해제
  • 조회끼리는 병렬, INSERT 는 혼자 → id 중복 · 줄 섞임 · 반쯤 쓴 데이터 읽기 방지
  • INSERT 후 새 (id → 위치) 를 다른 워커에 알린 뒤에 락 해제 → 이후 조회는 최신 인덱스
  • 대기 중인 쓰기가 있으면 새 읽기는 뒤에(기아 방지), 워커가 죽거나 시간을 넘기면 새로 만듦

8. 한계와 개선

없는 것생기는 문제개선 방향
UPDATE · DELETE · 트랜잭션읽고 고쳐 쓰기를 원자적으로 못 함BEGIN/COMMIT, 행 단위 락 · MVCC

보조 인덱스id 외 열은 항상 선형 탐색열마다 B+ 트리, UNIQUE
