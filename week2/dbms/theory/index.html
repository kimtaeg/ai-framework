1 큰 그림

DBMS 는 무엇인가

기초

데이터를 디스크에 안전하게 오래 저장하고, SQL 로 원하는 데이터를 찾아 주는 프로그램(MySQL, PostgreSQL 등).

쉽게 말하면아주 큰 도서관. 책(레코드)을 서가(파일)에 꽂아 두고, 찾아보기(인덱스)로 원하는 책을 빨리 찾게 해 주며, 여러 사람이 동시에 빌리고 반납해도 장부가 꼬이지 않게 관리합니다.

미니 DBMS 의 세 단계

Phase 1 · SQL 처리기

SQL 문자열 → 파싱 → 실행 → 파일에 저장/읽기. CLI 로 SQL 파일을 실행.

Phase 2 · B+ 트리 인덱스

id 가 자동으로 붙고 B+ 트리에 등록. id 조회가 100만 건에서도 0.04ms.

Phase 3 · API 서버

Phase 1+2 를 엔진으로 두고 스레드 풀로 요청을 병렬 처리.

공통

엔진은 저장소를 인터페이스로만 써서 파일 / 메모리를 바꿔 끼울 수 있음.

SQL 처리 흐름

과제 핵심

입력(SQL) → 토큰화 → 파싱(AST) → 실행 계획 → 실행 → 저장 / 결과.

"SELECT name FROM users WHERE id = 3"
   │ ① 토큰화 (lexer)    → [SELECT] [name] [FROM] [users] [WHERE] [id] [=] [3]
   │ ② 파싱 (parser)     → { type:'select', columns:['name'], table:'users', where:[{id = 3}] }
   │ ③ 계획 (planner)    → id 조건이 있음 → B+ 트리 인덱스 조회
   │ ④ 실행 (executor)   → 인덱스로 위치 찾기 → 그 줄만 읽기 → 조건 검사 → 열 고르기
   ▼ ⑤ 결과              → [['정트리']]
미니 DBMS 에서는Phase 1 에서 SQL 을 실행하면 이 다섯 단계가 아래 파이프라인 칸에 차례로 나옵니다. 코드는 sql.js(①②)와 engine.js(③④⑤).
핵심 정리SQL 은 "무엇을" 원하는지만 말하고, "어떻게" 찾을지는 DBMS 가 정합니다(선언형). 1주차 React 가 "화면이 어떻게 생겼는지" 만 말하고 바꾸는 방법은 diff 가 정한 것과 같은 생각입니다.
2 SQL 처리기 (Phase 1)

토크나이저와 파서

과제 핵심

글자를 의미 있는 조각(토큰)으로 자르고, 토큰 순서를 문법 규칙에 맞춰 구조(AST)로 바꿉니다.

  • 토크나이저: 예약어(SELECT…), 이름(users), 숫자, '문자열', 기호. 문자열 안의 '' 는 따옴표 하나. 주석과 공백은 버림. 각 토큰에 행·열 위치를 기록.
  • 재귀 하강 파서: 문법 규칙 하나 = 함수 하나(insert(), select(), condition()). 기대한 토큰이 아니면 "'FROM' 이(가) 필요한데 'users' 이(가) 있습니다 (1행 10열)".
  • BETWEEN a AND b 는 파싱 단계에서 >= a 와 <= b 두 조건으로 풀어 둠 → 실행기는 비교만 알면 됨.

3 인덱스 (Phase 2)


        

          
인덱스란
과제 핵심

          
"값 → 레코드 위치" 지도. 처음부터 끝까지 읽지(O(n)) 않고 바로 찾게(O(log n)) 합니다.

          
쉽게 말하면책 뒤의 "찾아보기". 본문을 처음부터 넘기지 않고, 찾아보기에서 쪽 번호를 보고 바로 펼칩니다.

          
    
            
  • 대가: 공간이 더 들고, INSERT 마다 인덱스도 고쳐야 해서 쓰기가 느려집니다.
    • 
            
  • 해시 인덱스 vs B+ 트리: 해시는 = 만 O(1), 범위·정렬은 못 함. B+ 트리는 둘 다 → 대부분의 DB 기본값.
    • 
            
  • 못 쓰는 경우: 인덱스 없는 열, !=, 열에 함수를 씌운 조건, 결과가 너무 많을 때(전체 읽기가 더 쌈).
    • 
          

          
미니 DBMS 에서는id 에만 인덱스. 100만 건에서 id = ? 0.038ms vs email = ? 1,032ms (약 27,000배). Phase 2 실험 2.

        


        

          
B 트리 vs B+ 트리
과제 핵심

          
B+ 트리는 데이터를 리프에만 두고 리프끼리 연결합니다. 노드가 넓어 트리가 낮고, 범위 검색은 옆으로 읽기만 하면 됩니다.

          

            
B 트리
모든 노드에 키와 데이터. 찾는 키가 위쪽에 있으면 일찍 끝남. 범위 검색은 트리를 오르내려야 함.

            
B+ 트리 (채택)
데이터는 리프에만, 내부 노드는 길 안내용 키만 → 노드에 키를 더 많이 넣어 트리가 낮음. 리프끼리 연결 리스트.

          

          
삽입과 분할

          
    
            
  1. 루트에서 이진 탐색으로 내려가 리프를 찾고 정렬 위치에 넣는다.
    2. 
            
  2. 키가 차수-1 개를 넘으면 반으로 쪼갠다. 리프는 오른쪽 첫 키를 복사해 부모로, 내부 노드는 가운데 키를 이동해 부모로.
    3. 
            
  3. 부모도 넘치면 위로 반복. 루트가 쪼개지면 높이 +1 → 모든 리프가 항상 같은 깊이.
    4. 
          

          
차수 m, 원소 n 이면 높이 ≈ logm(n). m = 64, n = 100만 → 높이 4.

          
미니 DBMS 에서는bptree.js 의 check() 가 정렬·키 개수·같은 깊이·리프 연결을 검사하고, 테스트가 차수 3~8 에서 무작위 2,000개로 확인. Phase 2 실험 1 에서 분할을 눈으로 봅니다.

4 API 서버 (Phase 3)


        

          
스레드 풀
과제 핵심

          
스레드를 미리 N 개 만들어 두고, 요청이 오면 쉬는 스레드에게 맡깁니다. 모두 바쁘면 대기열에서 기다립니다.

          
쉽게 말하면콜센터 상담원. 전화가 올 때마다 새로 뽑으면 시간이 걸리고, 전화가 몰리면 상담원이 끝없이 늘어납니다. 미리 N 명을 두고, 다 통화 중이면 대기 음악을 틀어 줍니다.

          
    
            
  • 왜: 생성 비용 절약, 동시 실행 수 상한(메모리·CPU 보호), 대기열로 폭주 흡수
    • 
            
  • 몇 개?: CPU 위주 작업이면 코어 수 근처, I/O 대기가 많으면 더 많이
    • 
            
  • Node 에서: worker_threads. 워커끼리 메모리를 공유하지 않고 메시지로 통신
    • 
            
  • 장애 대비: 워커가 죽으면 새로 만들고, 너무 오래 걸리면(timeout) 끊음
    • 
          

        


        

          
락과 멀티 스레드 동시성 이슈
과제 핵심

          
여러 스레드가 같은 데이터를 동시에 바꾸면 결과가 꼬입니다. 읽기/쓰기 락으로 "읽기는 함께, 쓰기는 혼자" 를 지킵니다.

          

            
문제예미니 DBMS 의 해결

            
경쟁 상태두 INSERT 가 동시에 "다음 id = 5" 를 읽고 둘 다 5테이블 쓰기 락

            
찢어진 쓰기두 스레드가 같은 파일에 동시에 써서 줄이 섞임쓰기 락 + 버퍼째 기록

            
더티 리드쓰는 도중의 반쪽 데이터를 읽음쓰기 중에는 읽기도 대기

            
캐시 불일치워커 A 가 넣은 행을 워커 B 의 인덱스가 모름쓰기 후 모든 워커에 알림, 그 다음에 락 해제

            
교착 상태A 는 users→products, B 는 반대 순서로 잠금항상 이름 순서로 잠금

            
기아읽기가 끝없이 와서 쓰기가 영원히 못 함기다리는 쓰기가 있으면 새 읽기는 뒤에

          

          
미니 DBMS 에서는lock.js 의 RWLock 과 LockManager. 테스트: 동시 INSERT 60개 → id 1~60 빈틈없이, 쓰는 중 읽기는 기다렸다가 새 행을 봄. Phase 3 실험 1.

          
주의실제 DBMS 는 테이블보다 잘게 행 단위 락을 쓰고, 읽기가 쓰기를 기다리지 않도록 옛 버전을 보여 주는 MVCC 를 씁니다(PostgreSQL, InnoDB).

면접 · 발표 예상 질문
과제 핵심

          

            
            
          

          
SQL 한 줄은 어떻게 처리되나요?
토크나이저가 글자를 토큰으로 자르고, 재귀 하강 파서가 AST 를 만들고, 실행 계획기가 id 조건이 있으면 B+ 트리를 쓰기로 정하고, 실행기가 파일의 해당 위치에서 줄을 읽어 조건 검사 후 결과를 돌려줍니다.

          
데이터는 파일에 어떻게 저장하나요?
테이블 하나 = 파일 하나, 한 줄 = 레코드 하나의 CSV 비슷한 형식입니다. 쉼표·따옴표는 따옴표로 감싸고 NULL 은 \N, 줄바꿈은 \n 으로 바꿔 한 줄을 지킵니다. 그래서 바이트 위치로 한 줄만 읽을 수 있습니다.

          
왜 B+ 트리인가요? 해시 인덱스는 안 되나요?
해시 인덱스는 = 조회만 빠르고 범위·정렬을 못 합니다. B+ 트리는 = 와 범위 모두 O(log n) 이고, 리프 연결로 범위를 순서대로 읽으며, 노드가 넓어 높이가 낮아서 디스크 읽기 횟수가 적습니다.

          
WHERE id = ? 에서 B+ 트리를 어떻게 쓰나요?
INSERT 때 id → 파일 위치를 B+ 트리에 등록해 두고, SELECT 의 계획기가 id 의 = 조건을 보면 트리에서 위치를 찾아 그 줄만 읽습니다.

          
100만 건에서 인덱스와 선형 탐색 차이는?
id = ? 는 평균 0.038ms, email = ? 는 1,032ms 로 약 2만 7천 배 차이였습니다. 선형 탐색은 데이터에 비례해 느려지고 인덱스는 높이(4)만큼만 내려갑니다.

          
스레드 풀에서 어떤 동시성 이슈가 있었고 어떻게 해결했나요?
INSERT 끼리 같은 id 를 받거나 파일 쓰기가 섞이는 문제는 테이블 쓰기 락으로, 워커마다 다른 인덱스 문제는 쓰기 후 다른 워커에 알린 뒤 락을 풀어서 해결했습니다. 조회는 읽기 락이라 병렬, 교착은 잠금 순서 고정, 쓰기 기아는 대기열 순서로 막았습니다.

          
다른 팀과의 차별점은?
행·열 위치가 있는 SQL 에러, 결과에 드러나는 실행 계획, 바이트 offset 기반 한 줄 읽기, B+ 트리 구조 검증, 읽기/쓰기 락 + 인덱스 알림을 쓰는 스레드 풀, 그리고 세 단계를 모두 눈으로 보는 Phase 페이지.
