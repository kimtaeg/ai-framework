1

B+ 트리의 차수와 높이

핵심 질문이진 탐색 트리도 O(log n) 인데, 왜 DBMS 는 자식이 수백 개인 트리를 쓸까?
직관도서관에서 책을 찾을 때 "왼쪽 아니면 오른쪽" 을 20번 고르는 것보다, 층 안내판(수백 개 구역)을 3번 보는 게 빠릅니다. 특히 안내판 하나 보러 갈 때마다 계단을 올라야 한다면.

원리

높이 ≈ logm(n). 메모리에서는 노드 방문 비용이 비슷하지만 디스크에서는 노드 하나 = 디스크 읽기 한 번(수 ms). 그래서 한 번 읽을 때 최대한 많은 키(한 페이지)를 가져오는 넓은 노드가 유리합니다. 넓은 노드 안에서는 이진 탐색이 메모리에서 일어나 싸고요.

실험 1 순서대로 넣은 트리의 높이
생각 실험: 그럼 차수를 100만으로 하면 높이 1 이니 최고 아닌가?
노드 하나를 읽는 비용이 노드 크기에 비례해 커집니다. 디스크는 페이지(4~16KB) 단위로 읽으므로 그보다 큰 노드는 여러 번 읽어야 하고, 삽입 때 노드 안에서 원소를 옮기는(splice) 비용도 O(m) 입니다. 그래서 "한 페이지에 꽉 차는 크기" 가 최적입니다.
내 코드에서 엔진 기본 차수 64(new Database(storage, { order })). 100만 건에서 높이 4.
2

순서대로 넣으면 노드가 반만 찬다

핵심 질문자동 증가 id 는 늘 맨 끝에 들어가니 B+ 트리에 가장 쉬운 경우 아닐까?
직관책장 한 칸이 차면 반을 옆 칸으로 옮기는 규칙인데, 새 책은 항상 맨 오른쪽에만 꽂힌다면? 옮겨 놓은 왼쪽 반 칸은 영원히 반만 찬 채로 남습니다.

원리

분할은 노드를 반으로 나누는데, 순차 삽입에서는 왼쪽 노드에 다시는 키가 안 들어옵니다. 그래서 리프 채움률이 50% 근처에 머무르고, 같은 데이터에 노드가 두 배 가까이 필요해 높이도 커질 수 있습니다. 무작위 삽입은 왼쪽 노드도 계속 채워져서 약 70% 가 됩니다. 실제 DBMS 는 "맨 끝 삽입" 을 감지해 새 키 하나만 새 노드로 보내는 분할을 해서 순차 삽입을 거의 100% 로 채웁니다.

실험 2 차수 16, 2만 개
더 깊이: 그럼 무작위 id(UUID)를 기본 키로 쓰면 더 좋은 걸까?
채움률은 높아지지만 삽입 위치가 트리 전체에 흩어져서, 디스크 기반 DBMS 에서는 매번 다른 페이지를 읽고 써야 하고 캐시 효율이 크게 떨어집니다. 그래서 실무에서는 순차 id 를 쓰거나, 시간 순으로 정렬되는 UUIDv7 같은 키를 씁니다.
내 코드에서 #splitLeaf() 의 mid = Math.ceil(keys.length / 2). 개선하려면 "넣은 키가 노드의 마지막이면 오른쪽 노드에 그 키만" 으로 바꿉니다.
3

인덱스는 공짜가 아니다

핵심 질문인덱스가 조회를 수만 배 빠르게 한다면, 왜 모든 열에 인덱스를 만들지 않을까?
직관책 뒤의 "찾아보기" 는 찾을 때는 편하지만, 책에 한 쪽을 끼워 넣을 때마다 찾아보기의 쪽 번호도 고쳐야 합니다. 찾아보기가 열 개면 열 번 고쳐야 하고요.

원리

INSERT 한 번마다 B+ 트리에도 키를 넣고, 넘치면 분할합니다. 인덱스가 여러 개면 그 일을 인덱스 수만큼 합니다. 메모리(디스크)도 노드만큼 더 씁니다. 그래서 인덱스는 자주 찾는 열에만 만들고, 쓰기가 아주 많은 테이블(로그 등)은 인덱스를 줄입니다. 읽기를 빠르게 하는 대신 쓰기와 공간을 내주는 교환입니다.

실험 3 5만 건: 파일에만 쓰기 vs 파일 + B+ 트리
더 깊이: 그럼 실제 DBMS 는 인덱스를 어떻게 고를까?
사람(DBA·개발자)이 질의 패턴을 보고 만듭니다. 실행 계획(EXPLAIN)으로 어떤 질의가 전체 읽기를 하는지 찾고, 그 조건 열에 인덱스를 추가합니다. 여러 열을 함께 쓰는 질의에는 복합 인덱스(예: (user_id, created_at))를 쓰는데, 열 순서가 중요합니다 — 앞 열부터 정렬되기 때문입니다.
내 코드에서 Database.insert() 의 t.index.insert(id, loc). 미니 DBMS 는 id 인덱스 하나만 있습니다.
4

범위가 넓으면 인덱스가 오히려 손해

핵심 질문인덱스가 있으면 항상 인덱스를 쓰는 게 좋을까? 전체의 절반을 읽는 질의라면?
직관책에서 단어 하나를 찾을 때는 찾아보기가 빠르지만, 책의 절반을 읽어야 한다면 찾아보기의 쪽 번호를 하나하나 따라가는 것보다 그냥 처음부터 넘기는 게 빠릅니다.

원리

인덱스로 찾은 레코드는 파일 여기저기에 흩어져 있어서 하나마다 따로 찾아가 읽어야 합니다(임의 접근). 전체 읽기는 처음부터 쭉 이어서 읽습니다(순차 접근). 디스크는 순차 읽기가 임의 읽기보다 수십~수백 배 싸서, 결과가 전체의 몇 % 를 넘으면 전체 읽기가 더 빠릅니다. 실제 DBMS 의 최적화기는 통계(행 수, 값 분포)로 이 비율(선택도)을 추정해 계획을 고릅니다.

실험 4 2만 건에서 id 범위로 0.1% ~ 100% 읽기

읽은 레코드 수는 실제 엔진으로 셉니다. 시간은 "임의 읽기 1건 0.1ms, 순차 읽기 1건 0.002ms" 라는 단순한 디스크 비용 모델로 환산한 값입니다(메모리에서는 차이가 작음).

더 깊이: 미니 DBMS 의 실행 계획기는 이걸 알까?
모릅니다. id 조건이 있으면 무조건 인덱스를 씁니다(규칙 기반). 데이터가 메모리 파일 캐시에 있으면 임의 읽기도 싸서 대부분 괜찮지만, 디스크라면 넓은 범위에서 손해입니다. 개선하려면 테이블 행 수와 범위 크기로 결과 수를 추정해 일정 비율을 넘으면 full-scan 을 고르게(비용 기반) 바꿉니다.
내 코드에서 choosePlan() — 조건만 보고 고르는 규칙 기반. 결과의 plan.scanned 로 실제로 읽은 수를 확인할 수 있습니다.
5

작은 실행 계획기가 하는 일

핵심 질문WHERE 에 조건이 여러 개면 어떤 조건으로 먼저 찾을까? 조건의 순서가 중요할까?
직관"서울에 사는 김정글, 주민번호 123…" 을 찾을 때 주민번호(유일한 값)부터 보면 한 명만 남습니다. 어떤 정보로 먼저 좁힐지 고르는 것이 계획입니다.

원리

SQL 은 "무엇을" 원하는지만 말하고 "어떻게" 찾을지는 DBMS 가 정합니다(선언형). 미니 DBMS 의 계획기는 조건 중에 인덱스가 있는 id 조건을 골라 읽을 레코드를 좁히고, 나머지 조건은 읽은 레코드에 대해 검사합니다. 그래서 조건을 쓴 순서와 상관없이 같은 계획이 나옵니다. 모순된 조건(id = 3 AND id = 4)은 읽기 전에 "결과 없음" 으로 끝냅니다.

실험 5 질의 7개의 계획 (1,000건)
더 깊이: 실제 DBMS 의 최적화기는 무엇을 더 할까?
조인 순서 고르기(테이블이 여러 개면 경우의 수가 폭발), 여러 인덱스 중 가장 좁히는 것 고르기, 인덱스만으로 답하기(커버링 인덱스), 조건 다시 쓰기(상수 계산, 서브쿼리 펼치기) 등을 통계와 비용 모델로 합니다. PostgreSQL 의 EXPLAIN ANALYZE 로 실제 계획과 시간을 볼 수 있습니다.
내 코드에서 choosePlan() 과 select() — 계획은 "어떤 줄을 읽을지" 만 정하고, 조건 검사는 공통으로 take() 에서.
6

교착 상태 만들어 보기

핵심 질문락을 잘 걸면 안전하다면서, 락 때문에 서버가 멈출 수도 있다는 건 무슨 뜻일까?
직관좁은 골목에서 마주 본 차 두 대. 서로 상대가 비켜 주길 기다리면 영원히 못 지나갑니다.

원리

교착 상태의 네 조건: ① 자원을 혼자 씀(배타) ② 쥔 채로 다른 것을 기다림 ③ 남이 뺏을 수 없음 ④ 기다림이 원을 이룸. 넷 중 하나만 깨면 됩니다. 가장 쉬운 것이 ④: 모두가 같은 순서로 잡으면 원이 생길 수 없습니다. 실제 DBMS 는 대기 그래프에서 원을 찾아 한쪽 트랜잭션을 취소(롤백)하는 방법도 씁니다.

실험 6 T1: users → products, T2: products → users
더 깊이: 미니 DBMS 에서는 실제로 교착이 생길 수 있나?
API 서버는 한 요청이 쓰는 모든 테이블을 실행 전에 미리 파싱해서 알고, 한꺼번에 이름 순으로 잡습니다(② 와 ④ 를 동시에 막음). 그래서 생기지 않습니다. 트랜잭션이 생겨 "실행 도중에 필요한 테이블이 늘어나는" 구조가 되면 이 실험의 상황이 실제로 생깁니다.
내 코드에서 week2/dbms/lock.js 의 LockManager.acquire() — [...modes.keys()].sort() 순서로 잡습니다.
7

스레드를 늘리면 계속 빨라질까

핵심 질문워커가 4개일 때 초당 400건이면, 32개면 3,200건일까?
직관요리사(코어)가 4명인 주방에 주문 받는 직원(스레드)을 32명 두면? 요리사가 바쁘면 주문만 쌓입니다. 다만 요리사가 오븐 기다리는 시간(I/O)이 길면, 그동안 다른 요리를 시작할 직원이 많을수록 좋습니다.

원리

CPU 만 쓰는 작업은 코어 수에서 처리량이 멈춥니다. 그 이상은 코어를 번갈아 쓸 뿐이고 문맥 전환·메모리 비용만 늘어요. 디스크·네트워크를 기다리는 시간이 섞이면 그동안 놀던 코어를 다른 워커가 쓰므로 워커를 코어보다 많이 두는 게 유리합니다. 대략 워커 수 ≈ 코어 × (1 + 대기 시간 / 계산 시간).

실험 7 코어 4개, 작업 = 계산 10ms + 대기

이산 시간 시뮬레이션입니다(1ms 단위). 실제 측정은 테스트의 "느린 조회 4개 병렬" 에서 확인합니다.

더 깊이: 미니 DBMS 의 조회는 CPU 작업일까 I/O 작업일까?
선형 탐색은 파일을 읽지만(I/O) 대부분 운영체제 파일 캐시에 있어 실제로는 줄을 디코딩·비교하는 CPU 작업이 대부분입니다. 그래서 기본 워커 수를 min(4, 코어 수)로 잡았습니다. 데이터가 메모리보다 훨씬 커서 디스크를 정말 기다린다면 워커를 늘리는 게 이득입니다.
내 코드에서 createDbService({ workers = Math.min(4, Math.max(2, availableParallelism())) }).
8

미니 DBMS 의 한계 찾기

핵심 질문내 구현이 실제 DBMS 와 다른 곳은 어디이고, 어떤 상황에서 드러날까?

먼저 "무슨 일이 생길까?" 를 답해 보고 펼쳐 보세요. 발표의 "한계와 개선 방향" 질문 대비입니다.

상황 1. 두 클라이언트가 "잔액 확인 → 차감" 을 동시에 하면?
미니 DBMS 에는 UPDATE 도 트랜잭션도 없어서 "읽고 고쳐 쓰기" 를 하나로 묶을 방법이 없습니다. 실제 DBMS 는 트랜잭션(BEGIN … COMMIT)과 격리 수준, 행 단위 락이나 MVCC 로 이것을 원자적으로 처리합니다.
상황 2. INSERT 를 쓰는 도중 서버 전원이 꺼지면?
버퍼에 있던 줄은 사라지고, 쓰다 만 줄이 파일 끝에 남을 수 있습니다. 재시작 시 id 를 못 읽는 줄은 건너뛰지만 "응답은 성공했는데 데이터가 없는" 일이 생길 수 있습니다. 실제 DBMS 는 WAL(쓰기 전에 로그부터 디스크에 확정)로 커밋된 것은 반드시 지킵니다.
상황 3. 서버를 껐다 켤 때 100만 건이면?
B+ 트리가 메모리에만 있어서 켤 때마다 파일 전체를 읽어 다시 만듭니다(측정 0.47초, 워커마다). 1억 건이면 수십 초. 실제 DBMS 는 B+ 트리 자체를 디스크 페이지로 저장해서 켜자마자 씁니다.
상황 4. email 로 자주 찾는 서비스라면?
id 외의 열에는 인덱스가 없어서 매번 선형 탐색입니다(100만 건에 약 1초). 실제 DBMS 는 CREATE INDEX 로 열마다 B+ 트리를 만들고, UNIQUE 제약으로 중복도 막습니다. 예제 4번은 레디스로 이것을 흉내 냅니다.
상황 5. 반대로 이 구현이 잘한 점은?
실행 계획을 결과에 드러내고, 바이트 위치로 한 줄만 읽으며, 스레드 풀에서 락 + 인덱스 알림으로 동시 INSERT 의 정합성을 테스트로 증명했습니다(동시 INSERT 60개 → id 1~60). SQL 오류는 행·열 위치까지 알려 줍니다.
