B+ 트리 인덱스 Playground

INSERT 하면 id 가 자동으로 붙고, B+ 트리에 id → 레코드 위치가 등록됩니다. WHERE id = ? 는 이 트리로 바로 찾고, 다른 열 조건은 처음부터 끝까지 읽습니다. 노드가 넘쳐 쪼개지는 모습과 두 방식의 속도 차이를 직접 봅니다(week2/dbms/bptree.js).

B+ 트리 분할 · 검색 경로

노드에 키가 차수 - 1 개를 넘으면 반으로 쪼개고 가운데 키를 부모로 올립니다. 실제 데이터(행 위치)는 리프(파란 테두리)에만 있고, 리프끼리는 → 로 이어져 있어 범위 검색은 리프를 따라 옆으로 읽습니다. 모든 리프가 같은 깊이라 어떤 키든 높이만큼만 내려가면 됩니다.

왜 이진 탐색 트리가 아니라 B+ 트리?디스크는 한 번 읽을 때 큰 덩어리(페이지, 예: 16KB)로 읽습니다. 노드 하나에 키를 수백 개 넣으면 트리가 아주 낮아져서(100만 건도 높이 3~4) 디스크를 몇 번만 읽고 찾을 수 있습니다. 이진 트리는 높이가 20 이상이라 20번 읽어야 합니다.
성능 비교 인덱스(id) vs 선형 탐색(다른 필드)

같은 데이터에서 WHERE id = ?(B+ 트리) 200번과 WHERE email = ?(처음부터 끝까지) 5번의 평균 시간을 잽니다. 브라우저 메모리에서 하므로 30만 건까지만 고를 수 있어요.

100만 건 (과제 요구사항) — 실제 파일로 측정한 결과 node week2/dbms/bench.js --rows 1000000
INSERT 1,000,000건 2.09초 (파일 41.7MB, B+ 트리 높이 4) · id = ? 평균 0.038ms · email = ? 평균 1,032ms → 약 27,000배 · id 1,000건 범위 7.9ms · 재시작 시 인덱스 재구성 0.47초
