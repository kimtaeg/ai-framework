1 보는 방법: 예측 → 실행 → 확인 → 설명

실습 하나를 볼 때 이 4단계를 거치세요. 그냥 눌러보기만 하면 "잘 되네"로 끝나서 개념이 남지 않습니다.

① 예측누르기 전에 결과를 먼저 말해본다
→
② 실행SQL 을 실행한다
→
③ 확인실행 계획과 "읽은 레코드" 숫자를 본다
→
④ 설명예측과 다른 부분을 이론으로 설명한다

예시: Phase 1 에서 WHERE id = 3 과 WHERE name = '최디비'

단계내용
① 예측"둘 다 한 명만 나오니까 읽는 양도 같을 것 같다."
② 실행예시 두 개를 차례로 실행
③ 확인"id 는 읽은 레코드 1/5, name 은 5/5. 파일 줄도 하나 vs 전부 파랗게 표시."
④ 설명"id 에는 B+ 트리 인덱스가 있어서 위치를 바로 찾아 그 줄만 읽고, name 은 인덱스가 없어서 처음부터 끝까지 비교한다. 결과 수가 아니라 읽는 양이 성능을 정한다."
예측이 틀린 지점이 가장 많이 배우는 지점입니다. 틀리면 이론 페이지의 해당 섹션으로 돌아가 다시 읽으세요.

3 예제별로 꼭 답해볼 질문

답을 먼저 말해본 뒤 "힌트"를 열어 확인하세요.

📝 회원 가입

O'Brien 을 그대로 넣으면 왜 오류가 날까?

토크나이저가 'O' 에서 문자열을 끝내고, 뒤의 Brien' 을 이름으로 읽어 문법이 깨집니다. ' 를 '' 로 바꿔야 값 안의 따옴표가 됩니다.

나이에 글자를 넣으면 몇 명이 저장될까?

0명. 실행기가 모든 행을 먼저 검사하고 통과해야 저장하므로, 오류가 나면 아무것도 저장하지 않고 id 도 쓰지 않습니다.

📋 게시판 목록 캐시

최신 글 목록은 어떤 실행 계획일까?

WHERE id > 마지막id-5 라서 B+ 트리 범위 조회입니다. 2만 개가 있어도 5개만 읽습니다.

글을 쓰면 왜 캐시를 지워야 할까?

원본(DBMS)만 바뀌고 복사본(캐시)이 그대로면 TTL 이 끝날 때까지 새 글이 안 보입니다.

📄 페이지 넘기기

1,000쪽에서 OFFSET 방식은 몇 개를 읽을까?

앞의 9,990개를 읽고 버린 뒤 10개를 더 읽어 10,000개. id 기준은 10개만 읽습니다.

id 기준 방식의 단점은?

"정확히 500쪽으로 바로 가기" 는 그 앞 쪽의 마지막 id 를 알아야 해서 어렵습니다. 무한 스크롤처럼 다음 쪽으로만 가는 화면에 맞습니다.

✉️ 이메일로 찾기

왜 email 조건은 느릴까?

미니 DBMS 는 id 에만 인덱스가 있어서 email 조건은 선형 탐색입니다. 5만 명이면 평균 2만 5천 명을 읽습니다.

레디스 보조 인덱스의 위험은?

DB 와 레디스가 따로라서 한쪽만 바뀌면 어긋납니다(가입 실패 시 정리 등). 실제 DBMS 가 보조 인덱스를 직접 관리하는 이유입니다.

5 함께 쓰면 좋은 도구

터미널 (CLI)

  • node week2/dbms/cli.js run query.sql
  • node week2/dbms/cli.js exec "SELECT * FROM users WHERE id = 1"
  • node week2/dbms/cli.js seed users 1000000 · info

성능 · 서버

  • npm run bench:dbms — 100만 건 비교 (임시 폴더)
  • npm run dbms — 스레드 풀 서버 (포트 7000)
  • npm start — /api/sql 포함

샌드박스

샌드박스에서 tokenize() · parse() 로 처리기의 중간 결과를 직접 출력하고, sql() 결과 표에서 실행 계획을 확인합니다.
