1 큰 그림

React 란?

기초

상태(state)가 바뀌면 화면(UI)을 자동으로 다시 그려주는 UI 라이브러리. Meta 가 만들어 2013년에 공개했습니다.

쉽게 말하면엑셀을 떠올려 보세요. 셀에 =A1*2 라고 써 두면, A1 값만 바꿔도 결과 셀이 알아서 바뀌죠. React 도 같습니다. "이 데이터면 화면은 이렇게 생겼다"고 한 번 써 두면, 데이터가 바뀔 때 화면이 따라 바뀝니다.

명령형 vs 선언형

명령형 (직접 DOM 조작)

"어떻게" 바꿀지 하나하나 명령

count++;
el.textContent = count;
if (count > 10) el.classList.add('big');

선언형 (React)

"무엇이" 보여야 하는지만 기술

<span className={count > 10 ? 'big' : ''}>
  {count}
</span>

명령형은 화면이 커질수록 "데이터가 바뀌면 어디어디를 고쳐야 하지?"를 개발자가 전부 기억해야 합니다. 하나라도 놓치면 버그가 됩니다. 선언형은 그 일을 React 가 대신합니다.

UI = f(state)

화면은 상태를 넣으면 나오는 함수의 결과. 상태가 바뀌면 함수를 다시 실행한다.

React 의 세 기둥

① 컴포넌트UI 를 재사용 가능한 작은 조각으로 나눈다
② 선언적 렌더링상태를 바꾸면 화면이 따라온다
③ Virtual DOM 과 재조정바뀐 부분만 실제 DOM 에 반영한다
더 알아보기: 라이브러리 vs 프레임워크, react vs react-dom

React 는 "라이브러리"입니다. 화면 그리기에 집중하고 라우팅, 데이터 요청, 빌드 같은 기능은 직접 들어 있지 않습니다. 이런 것까지 포함한 것이 Next.js 같은 "프레임워크"입니다.

react 패키지는 컴포넌트와 Hooks 를, react-dom 은 브라우저 DOM 에 그리는 일을 맡습니다. 둘이 나뉘어 있어서 같은 React 로 React Native(모바일 앱)처럼 다른 대상에도 그릴 수 있습니다.

핵심 정리
  • React 는 상태가 바뀌면 화면을 자동으로 다시 그려주는 라이브러리
  • 개발자는 "어떻게"가 아니라 "무엇을" 그릴지만 쓴다 (선언형)

전체 흐름 한눈에

과제 핵심

버튼 하나를 눌렀을 때 React 안에서 일어나는 일. 이 페이지의 모든 주제가 이 흐름의 한 칸입니다.

  1. 사용자 이벤트버튼 클릭, 입력 등이벤트 시스템
  2. setState 호출새 값을 저장하고 다시 그려달라고 "예약"Batching
  3. Render: 컴포넌트 함수 다시 실행Hooks 가 저장해 둔 상태를 꺼내 쓰며 새 Virtual DOM 을 만든다Hooks 원리
  4. Diff: 이전 Virtual DOM 과 비교바뀐 곳만 골라 변경 목록(patch)을 만든다Diff
  5. Commit / Patch: 실제 DOM 반영변경 목록대로 DOM 을 최소한으로 고친다Patch
  6. 브라우저가 화면 그리기Reflow / RepaintReflow 와 Repaint
  7. useEffect 실행화면이 바뀐 뒤 해야 할 일 (데이터 요청, 타이머 등)useEffect
miniReact 에서는FunctionComponent.update() 한 함수 안에 3~7단계가 순서대로 들어 있습니다: render() → diff() → applyPatches() → effect 실행.
2 브라우저와 DOM

DOM, document, window

과제 핵심

DOM 은 HTML 문서를 자바스크립트가 다룰 수 있게 만든 객체 트리입니다.

쉽게 말하면HTML 파일은 "종이에 쓴 설계도"이고, DOM 은 브라우저가 그 설계도를 보고 실제로 지은 "집"입니다. 자바스크립트는 이 집의 벽지를 바꾸거나(속성 변경) 방을 늘리는(노드 추가) 일을 합니다.

window — 브라우저 창

전역 객체. setTimeout, location, history, localStorage, requestAnimationFrame 등을 가짐

document — 창 안의 문서

DOM 트리의 시작점. querySelector, createElement 로 노드를 찾고 만든다

자주 쓰는 DOM API

하고 싶은 일API
찾기querySelector, childNodes, parentNode
만들기createElement, createTextNode
붙이기 / 옮기기appendChild, insertBefore (이미 있는 노드면 이동)
바꾸기 / 지우기replaceChild, removeChild
속성 / 텍스트setAttribute, removeAttribute, nodeValue

헷갈리기 쉬운 두 가지

childNodes vs children

childNodes 는 텍스트와 주석까지 포함, children 은 엘리먼트만. 들여쓰기 공백도 텍스트 노드라서 childNodes 에 섞여 나옵니다.

attribute vs property

<input value="a"> 의 attribute 는 HTML 에 적힌 초기값, input.value property 는 지금 값. 사용자가 입력하면 property 만 바뀝니다.
miniReact 에서는Phase 1 이 로드될 때 들여쓰기 공백과 주석을 지워서(normalizeDom) childNodes 순서와 Virtual DOM 자식 순서를 1:1로 맞춥니다. value 와 checked 는 attribute 와 property 를 함께 바꿔서 입력창에도 바로 보이게 합니다.

과제 핵심

"DOM 이 실제로 바뀌었는지"를 브라우저가 알려주는 감시 카메라.

API무엇을 감지?예시 용도
MutationObserver자식 추가/삭제, 속성 변경, 텍스트 변경DOM 변경 기록, 외부 스크립트 감시
ResizeObserver요소 크기 변화반응형 차트

MutationObserver 는 변경이 생길 때마다 바로 부르지 않고, 모아서 비동기(microtask)로 한 번에 알려줍니다. 예전의 Mutation Events 는 변경마다 동기로 불려서 느렸고 지금은 쓰지 않습니다.

miniReact 에서는Phase 1, 2 모두 patch 직후 observer.takeRecords() 로 실제 DOM 변경 수를 세어 화면에 보여줍니다. "바뀐 곳만 고쳤다"를 숫자로 증명하는 장치입니다.

브라우저 렌더링과 Reflow / Repaint

과제 핵심

실제 DOM 이 "느린" 이유. 무엇을 바꾸느냐에 따라 브라우저가 다시 해야 하는 일의 양이 다릅니다.

쉽게 말하면방 하나의 크기를 바꾸면 옆방, 복도까지 다시 재야 합니다(Reflow). 벽지 색만 바꾸면 칠만 다시 하면 됩니다(Repaint). 가구를 살짝 밀어 보이게 하는 건 칠도 필요 없습니다(Composite).

렌더링 단계

HTML → DOM+CSS → CSSOM→Render Tree→Layout (Reflow)→Paint (Repaint)→Composite

버튼을 눌러 보세요.

단계하는 일일어나는 경우
Reflow크기와 위치를 다시 계산width, height, margin, 글자 크기, 노드 추가/삭제, 창 크기 변경
Repaint픽셀을 다시 칠함color, background, visibility, box-shadow
Composite레이어를 GPU 로 합성transform, opacity

실제 DOM 이 느린 이유

  • Reflow 는 한 요소만 바뀌어도 부모, 형제, 자식까지 연쇄적으로 다시 계산될 수 있다.
  • Reflow 가 일어나면 Repaint 와 Composite 도 따라온다. (Reflow ⊃ Repaint)
  • DOM 노드는 수백 개 속성을 가진 무거운 객체이고, JS 와 렌더링 엔진 사이를 오가는 호출에도 비용이 든다.
  • Layout Thrashing: 쓰기 → offsetHeight 읽기 → 쓰기 → 읽기를 반복하면, 읽을 때마다 레이아웃을 강제로 다시 계산한다.
정확히 말하면DOM 조작 한 번이 느린 게 아니라, 불필요하게 자주 조작해서 Reflow/Repaint 가 반복되는 게 문제입니다. 그래서 "바뀐 곳만, 모아서" 고치는 Virtual DOM 이 등장했습니다.
더 알아보기: 렌더링 최적화 팁
  • 애니메이션은 top/left 대신 transform/opacity (Composite 만 발생)
  • 읽기와 쓰기를 묶어서. 여러 노드는 DocumentFragment 에 모아 한 번에 붙이기
  • 화면 갱신은 requestAnimationFrame 으로 프레임에 맞추기
핵심 정리
  • 크기·위치 변경 = Reflow (가장 비쌈), 색 변경 = Repaint, transform = Composite
  • DOM 을 적게, 모아서 바꾸는 것이 성능의 핵심

Virtual DOM

과제 핵심

실제 DOM 의 구조를 흉내 낸 가벼운 자바스크립트 객체. "화면이 어떻게 생겨야 하는가"에 대한 설계도입니다.

쉽게 말하면집을 리모델링할 때 바로 벽부터 부수지 않죠. 새 설계도를 그려서 옛 설계도와 비교한 뒤 달라진 곳만 공사합니다. Virtual DOM 이 그 설계도입니다.

실제 HTML

<ul class="list">
  <li>사과</li>
</ul>

Virtual DOM (그냥 객체)

{
  type: 'ul',
  props: { class: 'list' },
  children: [
    { type: 'li', props: {},
      children: ['사과'] }
  ]
}

왜 필요한가

선언적 개발매번 화면 전체를 새로 그리는 것처럼 코드를 쓰면, 무엇을 바꿀지는 비교 알고리즘이 계산
변경 최소화메모리에서 먼저 비교하고, 바뀐 노드에만 DOM API 호출
어디든 그리기그냥 객체라서 브라우저, 모바일 앱, 서버 문자열 어디로든 변환 가능
흔한 오해: "Virtual DOM 이 DOM 보다 빠르다"아닙니다. 바꿀 곳을 정확히 알고 직접 고치는 게 가장 빠릅니다. Virtual DOM 은 "비교 비용"을 더 내는 대신, 개발자가 바꿀 곳을 관리하지 않아도 충분히 빠르게 해주는 절충안입니다. Svelte, SolidJS 처럼 Virtual DOM 없이 빌드할 때 바꿀 곳을 미리 계산하는 도구도 있습니다.
miniReact 에서는src/lib/vdom.js 에 세 가지 변환이 있습니다.
h(): 코드 → VNode  ·  domToVNode(): 실제 DOM → VNode  ·  createElement(): VNode → 실제 DOM
핵심 정리
  • Virtual DOM = 화면 설계도 역할을 하는 가벼운 JS 객체 트리
  • 목적은 "속도 자체"가 아니라 "선언적으로 개발하면서도 성능을 지키는 것"

JSX 와 React Element

기초

JSX 는 HTML 처럼 생긴 자바스크립트 문법입니다. 빌드할 때 함수 호출로 바뀝니다.

내가 쓰는 JSX

<Button color="blue">
  확인
</Button>

빌드 후 실제 코드

jsx(Button, {
  color: 'blue',
  children: '확인'
})
  • 결과물 React Element 는 { type, props, key } 를 담은 객체. 실제 DOM 이 아니라 설계도의 한 조각입니다.
  • 소문자(<div>)는 HTML 태그, 대문자(<Button>)는 컴포넌트. 그래서 컴포넌트 이름은 대문자로 시작해야 합니다.
  • {} 안에는 JS 표현식. class 대신 className, for 대신 htmlFor.
  • JSX 에 넣은 문자열은 자동 이스케이프되어 XSS 를 막습니다.
  • false, null, undefined 는 그려지지 않아서 {cond && <A/>} 로 조건부 렌더링을 합니다.
주의{items.length && <List/>} 에서 길이가 0 이면 화면에 0 이 찍힙니다. {items.length > 0 && ...} 로 쓰세요.
miniReact 에서는빌드 도구 없이 h('div', props, ...children) 를 직접 호출합니다. JSX 가 변환된 결과를 손으로 쓰는 셈입니다.
3 Diff 와 Patch

Diff 알고리즘 동작 방식

과제 핵심

이전 설계도와 새 설계도를 비교해서 "바뀐 곳 목록"을 만드는 과정. React 에서는 재조정(Reconciliation)이라고 부릅니다.

쉽게 말하면틀린 그림 찾기인데, 규칙을 정해서 빨리 찾는 겁니다. "같은 줄끼리만 비교한다", "종류가 다르면 그 부분은 통째로 새로 그린다".

왜 규칙이 필요할까

두 트리를 완벽하게 비교하는 알고리즘은 O(n³) 입니다. 노드 1,000개면 10억 번 연산이라 실시간 화면에 못 씁니다. 그래서 React 는 두 가지 가정으로 O(n), 즉 1,000번 정도로 줄입니다.

가정 ① 타입이 다르면 다른 트리<div> 가 <span> 이 되면 하위를 비교하지 않고 통째로 새로 만든다
가정 ② 형제는 key 로 구분리스트에서 key 가 같으면 같은 항목으로 보고 재사용한다
+ 같은 레벨끼리만 비교다른 부모 밑으로 옮겨진 노드는 "이동"이 아니라 "삭제 + 생성"

비교 순서

  1. 같은 위치의 두 노드를 꺼낸다
  2. 한쪽이 없으면?추가 또는 삭제
  3. 타입이 다르면?교체하고 끝 (하위는 안 봄)
  4. 텍스트면?내용이 다를 때만 텍스트 변경
  5. 같은 태그면?속성을 비교하고, 자식들로 내려가 1번부터 반복
핵심 정리
  • 완벽한 비교(O(n³)) 대신 두 가지 가정으로 O(n) 에 비교
  • 타입이 다르면 교체, 같으면 속성 비교 후 자식으로 재귀

최소 변경을 위한 5가지 핵심 케이스

과제 핵심

Diff 결과는 결국 이 다섯 가지(+이동) 중 하나입니다.

① INSERT 추가
<ul><li>A</li></ul>→<ul><li>A</li><li>B</li></ul>

없던 노드가 생김 → 새 DOM 을 만들어 insertBefore

② REMOVE 삭제
<ul><li>A</li><li>B</li></ul>→<ul><li>A</li></ul>

있던 노드가 사라짐 → removeChild

③ REPLACE 교체
<p>안녕</p>→<h3>안녕</h3>

태그가 바뀜 → 하위 전체를 새로 만들어 replaceChild

④ TEXT 텍스트
<p>안녕</p>→<p>반가워</p>

글자만 바뀜 → nodeValue 만 수정 (가장 저렴)

⑤ PROPS 속성
<p class="a">→<p class="b">

같은 태그, 속성만 바뀜 → 바뀐 속성만 setAttribute

+ MOVE 이동
[A, B, C]→[C, A, B]

key 가 같은 노드의 위치만 바뀜 → 기존 노드를 옮김 (새로 만들지 않음)

miniReact 에서는src/lib/diff.js 가 정확히 이 6가지를 INSERT / REMOVE / REPLACE / TEXT / PROPS / MOVE 패치로 만듭니다. Phase 1 화면의 "Patch 로그"에서 실제로 어떤 케이스가 나왔는지 색깔별로 볼 수 있습니다.

key 의 역할

과제 핵심

리스트에서 "이 항목이 아까 그 항목이다"라고 알려주는 이름표.

쉽게 말하면교실에서 학생들이 자리를 바꿨을 때, 이름표가 없으면 선생님은 "1번 자리 학생", "2번 자리 학생"으로만 기억합니다. 자리가 바뀌면 사람을 헷갈리죠. 이름표(key)가 있으면 누가 어디로 갔는지 정확히 압니다.
직접 해보기: key 를 index 로 쓰면 무슨 일이?

입력칸에 메모가 들어 있습니다. "맨 앞에 추가"를 눌러 두 리스트를 비교해 보세요.

key = index (순서)

    key = id (고유 값)

      정리하면

      key = indexkey = 고유 id
      맨 앞에 추가하면모든 항목이 "내용이 바뀐 것"으로 보여 전부 수정"1개 추가"로 정확히 인식
      입력값 같은 상태엉뚱한 항목에 붙음 (위 예제)항목을 따라감
      써도 되는 경우절대 바뀌지 않는 정적 리스트항상 권장
      • key 는 형제 사이에서만 고유하면 된다. 전역으로 고유할 필요는 없다.
      • Math.random() 처럼 매번 바뀌는 값은 쓰면 안 된다. 매번 전부 새로 만들어진다.

      key 리스트의 순서가 바뀌면 "몇 개를 옮겨야 하나"가 문제입니다. [A,B,C,D] → [B,C,D,A] 를 앞에서부터 단순 비교하면 B, C, D 를 하나씩 앞으로 옮겨 3번 이동합니다.

      miniReact 는 LIS(최장 증가 부분 수열)를 구해서 "이미 순서가 맞는 가장 긴 묶음"(B, C, D)은 그대로 두고, 나머지(A)만 옮깁니다. 그래서 1번만 이동합니다. Vue 3 와 같은 방식이고, React 는 앞에서부터 한 번 훑는 더 단순한 방식을 씁니다.

      실제 DOM 에 반영하기 (Patch)

      과제 핵심

      Diff 가 만든 "변경 목록"을 받아서, 실제 DOM 에 하나씩 적용하는 단계.

      쉽게 말하면Diff 는 "공사 지시서"를 쓰는 사람, Patch 는 지시서대로 공사하는 사람입니다. 지시서에는 "3층 2번째 방 벽지를 파란색으로"처럼 위치와 할 일이 적혀 있습니다.

      패치 하나의 모양

      { type: 'TEXT',  path: [0, 2, 1], text: '새 텍스트' }       // 루트 → 0번 자식 → 2번 자식 → 1번 자식
{ type: 'PROPS', path: [1], changes: [{ name: 'class', value: 'on' }] }
{ type: 'MOVE',  path: [0, 2], from: 3, to: 0 }              // [0,2] 의 자식 중 3번을 0번 자리로

      path 는 루트에서 childNodes[i] 를 따라 내려가는 주소입니다.

      케이스별 DOM API

      패치실제로 호출하는 DOM API
      INSERTparent.insertBefore(createElement(vnode), 기준노드)
      REMOVEparent.removeChild(child)
      REPLACEparent.replaceChild(새노드, 기존노드)
      TEXTtextNode.nodeValue = text
      PROPSsetAttribute / removeAttribute, 이벤트는 핸들러만 교체, value·checked 는 property 도 갱신
      MOVEparent.insertBefore(기존노드, 기준노드) (이미 있는 노드라 이동만 됨)

      순서가 중요한 이유

      앞의 패치가 DOM 을 바꾸면 뒤 패치의 주소(path)가 어긋날 수 있습니다. 그래서 한 부모 안에서는 이 순서를 지킵니다.

      1. 삭제는 뒤에서부터앞을 먼저 지우면 뒤 항목의 번호가 당겨지기 때문
      2. 이동과 추가로 자리 확정
      3. 그다음 자식 안쪽으로 내려가서 비교자리가 확정된 뒤라 번호가 안 바뀜
      miniReact 에서는src/lib/patch.js 의 applyPatches() 가 이 일을 합니다. 루트가 교체될 수 있어서 항상 새 루트 노드를 돌려줍니다.
      핵심 정리
      • 패치 = "어디(path) + 무엇을(type)" 지시서
      • 삭제는 뒤에서부터, 위치 확정 후 자식 비교 → 주소가 어긋나지 않음

      React 가 실제 DOM 을 바꾸는 방식: Render 와 Commit

      과제 핵심

      React 의 업데이트는 "계산"과 "반영" 두 단계로 나뉩니다.

      쉽게 말하면Render 는 "공사 계획 짜기", Commit 은 "실제 공사"입니다. 계획은 중간에 바꾸거나 버려도 되지만, 공사를 반쯤 하다 멈추면 집이 엉망이 되니 한 번에 끝냅니다.
      setState→Render (계산)→Commit (DOM 반영)→Paint→useEffect
      Render 단계Commit 단계
      하는 일컴포넌트 함수 실행 → 새 트리 → 이전과 비교 → 바뀐 곳 표시표시된 변경을 실제 DOM 에 한 번에 반영, ref 연결
      중단 가능?가능 (멈추고, 버리고, 다시 시작)불가능 (반쯤 바뀐 화면을 보여주면 안 됨)
      부수효과없어야 함 (순수 함수)여기서 발생
      그래서 컴포넌트 본문은 순수해야 합니다Render 는 여러 번 실행되거나 버려질 수 있습니다. 렌더 중에 API 요청을 보내거나 전역 변수를 바꾸면 예측할 수 없는 버그가 생깁니다. 부수효과는 이벤트 핸들러나 useEffect 로 옮기세요.
      miniReact 에서는render()(순수 계산) → diff() → applyPatches()(반영) 로 같은 구조를 따릅니다. 다만 Render 를 중간에 멈출 수는 없습니다.

      Fiber 아키텍처

      심화

      React 16 부터 쓰는 엔진. 렌더링 작업을 잘게 쪼개서, 멈췄다가 이어서 할 수 있게 만들었습니다.

      쉽게 말하면예전 React 는 숙제를 시작하면 끝날 때까지 전화도 안 받는 학생이었습니다. Fiber 는 숙제를 문제 단위로 쪼개서, 한 문제 풀 때마다 "급한 전화 왔나?" 확인하는 학생입니다.

      왜 만들었나

      React 15 까지는 트리를 재귀 함수로 비교했습니다. 재귀는 시작하면 끝날 때까지 멈출 수 없어서, 트리가 크면 그동안 타이핑과 애니메이션이 끊겼습니다. (부드러운 화면은 한 프레임을 약 16ms 안에 끝내야 합니다.)

      Fiber 의 구조: 연결 리스트

            App
       │ child
       ▼
     Header ──sibling──▶ TodoList
                           │ child
                           ▼
                         Item ──sibling──▶ Item
   (모든 노드는 return 으로 부모를 가리킴)

      재귀 대신 이 화살표를 따라 반복문으로 돌기 때문에, 아무 데서나 멈추고 "다음엔 여기부터"를 기억할 수 있습니다.

      더 알아보기: Fiber 객체, 더블 버퍼링, Lane
      fiber = {
  type, key, stateNode,      // 컴포넌트 종류, 실제 DOM
  child, sibling, return,    // 첫 자식, 다음 형제, 부모
  memoizedState,             // ← Hooks 가 여기 연결 리스트로 저장됨
  flags,                     // 이번에 할 DOM 작업 (삽입/수정/삭제)
  lanes,                     // 우선순위
  alternate                  // 반대편 트리의 같은 Fiber
}

      더블 버퍼링: 화면에 보이는 current 트리와 다음 화면을 만드는 workInProgress 트리를 둘 다 유지합니다. 다 만들면 포인터만 바꿔서 교체합니다. 게임이 다음 프레임을 뒤에서 그려 두고 한 번에 바꾸는 것과 같습니다.

      Lane: 업데이트마다 비트로 된 우선순위가 붙습니다. 클릭·타이핑은 높게, startTransition 으로 감싼 업데이트는 낮게 처리해서 급한 일부터 합니다.

      function Avatar({ user, size = 48 }) {
  return <img src={user.photo} width={size} alt={user.name} />;
}
<Avatar user={me} size={64} />

      State 와 불변성

      과제 핵심

      State 는 컴포넌트가 기억하는, 시간이 지나며 바뀌는 값입니다.

      이건 state 일까? 체크리스트

      ✕시간이 지나도 안 바뀐다 → 상수
      ✕부모에게 props 로 받는다 → props
      ✕다른 값으로 계산할 수 있다 → 렌더 중 계산 (예: 완료 개수)
      ✕화면과 상관없다 → useRef
      ✓위에 다 해당 안 되고, 바뀌면 화면도 바뀌어야 한다 → state

      같은 정보를 두 곳에 두면 둘이 어긋나는 버그가 생깁니다. 정보는 한 곳에만 (Single Source of Truth).

      불변성: 고치지 말고 새로 만들기

      ✕ 직접 수정

      todos.push(newTodo);
setTodos(todos);
// 같은 배열 → React: "안 바뀌었네" → 화면 그대로

      ✓ 새로 만들기

      setTodos([...todos, newTodo]);
setUser({ ...user, name: 'Kim' });
// 새 배열 → 바뀐 걸 바로 앎
      왜?React 는 바뀌었는지를 이전 === 다음 으로 확인합니다(참조 비교). 상자 안을 다 뒤져보는 대신 "상자 자체가 바뀌었나"만 봐서 빠릅니다. 그래서 상자째로 바꿔줘야 합니다.
      miniReact 에서는Phase 1 의 뒤로가기가 이 원리로 동작합니다. Virtual DOM 을 절대 수정하지 않으니, 복사 없이 참조만 저장해도 과거 상태가 그대로 남습니다.

      State 는 어디에 둘까: 상태 끌어올리기

      과제 핵심

      여러 컴포넌트가 같은 state 를 쓰면, 가장 가까운 공통 부모로 state 를 옮깁니다 (Lifting State Up).

      부모 state 보관 · setState
      ⬇ props 로 데이터 전달
      ⬆ 콜백으로 "바꿔줘" 요청
      자식 A
      자식 B
      • 데이터는 위에서 아래로만 흐른다 (단방향). 자식은 부모 state 를 직접 못 바꾸고, 받은 함수를 호출해 요청한다.
      • 한 방향이라 "이 값을 누가 바꿨지?" 추적이 쉽다.
      • 어디에 둘까: 그 state 를 쓰는 모든 컴포넌트의 가장 가까운 공통 조상. 너무 위면 불필요한 리렌더링이 늘고, 너무 아래면 공유가 안 된다.
      • 아주 깊이 전달해야 하는 문제(Props Drilling)는 Context 나 상태 관리 라이브러리로 푼다.
      miniReact 에서는과제 조건대로 모든 state 가 루트 App 에만 있고, 자식에서 Hook 을 부르면 에러가 납니다. 극단적인 Lifting State Up 입니다.

      리렌더링이 일어나는 조건

      기초

      "렌더링" = 컴포넌트 함수를 다시 호출하는 것. DOM 을 다시 그리는 것과는 다릅니다.

      ① 내 state 가 바뀜setState
      ② 부모가 리렌더링됨props 가 같아도 자식은 기본적으로 다시 렌더링
      ③ 구독한 Context 가 바뀜useContext
      흔한 오해: "props 가 바뀌어야 리렌더링된다"아닙니다. 부모가 렌더링되면 자식도 렌더링됩니다. props 가 같을 때 건너뛰려면 React.memo 를 써야 합니다.

      렌더링이 일어나도 비교 결과 바뀐 게 없으면 DOM 은 건드리지 않습니다. 그래서 대부분의 리렌더링은 문제가 되지 않습니다.

      제어 컴포넌트와 비제어 컴포넌트

      기초

      입력창의 값을 누가 들고 있느냐의 차이.

      제어 (Controlled) — React 가 주인

      <input value={text}
  onChange={e => setText(e.target.value)} />

      즉시 검증, 자동 포맷, 버튼 비활성화가 쉬움

      비제어 (Uncontrolled) — DOM 이 주인

      <input defaultValue="a" ref={inputRef} />
// 필요할 때 inputRef.current.value

      코드가 짧고 타이핑마다 렌더링하지 않음. 파일 입력은 항상 비제어

      React 의 onChange 는 브라우저 change 와 달리 글자를 칠 때마다 발생합니다. value 만 주고 onChange 를 안 주면 입력이 막힙니다.

      이벤트 시스템

      심화

      React 는 버튼마다 리스너를 붙이지 않고, 루트 한 곳에서 모든 이벤트를 받아 나눠줍니다.

      쉽게 말하면아파트 집집마다 택배를 받는 대신, 관리실 한 곳에서 다 받아 호수별로 나눠주는 방식(이벤트 위임)입니다. 리스너 수가 줄어듭니다.
      • React 16 까지는 document, 17 부터는 루트 컨테이너에 리스너를 붙인다.
      • SyntheticEvent: 브라우저마다 다른 이벤트를 같은 모양으로 감싼 객체. 원본은 e.nativeEvent.
      • 기본 동작 막기는 e.preventDefault(). 캡처 단계는 onClickCapture.
      miniReact 에서는요소마다 네이티브 리스너를 한 번만 붙이고, 렌더링마다 핸들러 함수만 바꿔 끼웁니다. 위임 방식은 아닙니다.
      5 Hooks

      Hooks 동작 원리

      과제 핵심

      "함수는 매번 새로 실행되는데, 상태는 어떻게 유지할까?" — 이 질문의 답이 Hooks 입니다.

      쉽게 말하면함수는 실행이 끝나면 기억을 잃는 사람입니다. 그래서 함수 밖에 번호 붙은 사물함을 두고, 렌더링할 때마다 1번 사물함, 2번 사물함… 순서대로 열어 물건을 꺼내 씁니다. 사물함에는 이름이 없고 순서가 곧 이름입니다.
      직접 해보기: 렌더링할 때 사물함(hooks 배열)을 어떻게 여는지
      function Counter() {  const [count, setCount] = useState(0);  const [name, setName] = useState('철수');  const double = useMemo(() => count * 2, [count]);  return <p>{name}: {count} × 2 = {double}</p>;}
      hooks 배열 (함수 바깥에 저장)
      [0] useState 0
      [1] useState '철수'
      [2] useMemo 0
      hookIndex = - · 렌더 횟수 1
      철수: 0 × 2 = 0

      버튼을 누르면 함수가 다시 실행되며 사물함을 0번부터 순서대로 엽니다.

      let currentComponent, hookIndex;

function render(component) {
  currentComponent = component;
  hookIndex = 0;                         // 매 렌더마다 0번 사물함부터
  return component.fn(component.props);
}

function useState(initial) {
  const hooks = currentComponent.hooks;  // 함수 밖에 있는 사물함들
  const i = hookIndex++;                 // 호출 순서 = 사물함 번호
  if (!(i in hooks)) hooks[i] = { value: initial };   // 처음이면 초기값
  const slot = hooks[i];
  const setState = (v) => { slot.value = v; scheduleRender(); };
  return [slot.value, setState];
}
      • 실제 React 는 배열이 아니라 Fiber 의 memoizedState 에 연결 리스트로 저장합니다. 원리는 같습니다.
      • setState 는 클로저 덕분에 자기 사물함(slot)을 기억해서, 나중에 불려도 올바른 값을 바꿉니다.
      miniReact 에서는src/lib/component.js 의 FunctionComponent.hooks 배열이 이 사물함입니다. Phase 2 를 열고 브라우저 콘솔에 __app.hooks 를 치면 직접 볼 수 있어요.
      핵심 정리
      • 상태는 함수 밖(컴포넌트 인스턴스)의 배열에 저장된다
      • Hook 은 이름이 아니라 호출 순서로 자기 칸을 찾는다

      Hooks 규칙

      과제 핵심

      사물함을 순서로 찾기 때문에 생기는 두 가지 규칙.

      ① 최상위에서만 호출조건문, 반복문, 중첩 함수, 중간 return 뒤에서 호출 금지
      ② React 함수 안에서만함수 컴포넌트 또는 커스텀 Hook 안에서만

      조건문 안에서 부르면 왜 망가질까

      if (loggedIn) { const [a, setA] = useState(''); }   // 조건부!
const [b, setB] = useState(0);

      setState 는 무엇을 할까? 그리고 Batching

      과제 핵심

      setState 는 값을 "즉시" 바꾸는 함수가 아니라, "다시 그려줘"라고 예약하는 함수입니다.

      setState 가 하는 4가지 일

      1. 새 값 계산함수를 넘겼으면 이전 값을 넣어 실행
      2. 같은 값이면 멈춤Object.is(이전, 다음) 이면 아무것도 안 함 (bail-out)
      3. 저장Hook 사물함에 새 값 저장
      4. 다시 그리기 예약바로 그리지 않고 예약만. 이미 예약돼 있으면 또 예약하지 않음

        useEffect 와 useLayoutEffect

        과제 핵심

        화면이 바뀐 뒤에 해야 할 일(데이터 요청, 타이머, 구독)을 맡기는 Hook.

        쉽게 말하면"이사가 끝나면(화면 반영) 인터넷 신청하기(effect), 다음에 또 이사 가면 기존 인터넷 해지하기(cleanup)".
        useEffect(() => {
  const id = setInterval(tick, 1000);    // 설정
  return () => clearInterval(id);        // 정리 (cleanup)
}, [delay]);                             // 의존성 배열: delay 가 바뀔 때만 다시
        의존성 배열언제 실행?
        생략매 렌더 후
        []처음 1번 (cleanup 은 사라질 때)
        [a, b]처음 + a 나 b 가 바뀐 렌더 후

        실행 순서

        렌더→DOM 반영→useLayoutEffect→화면 그리기→이전 cleanup→새 effect

        useEffect

        보통 화면을 그린 뒤 실행. 화면 표시를 막지 않음. 대부분 이걸 쓴다.

        useLayoutEffect

        DOM 반영 직후, 그리기 전 실행. 요소 크기를 재서 위치를 정하는 툴팁처럼 깜빡임을 막아야 할 때만.
        • cleanup 은 사라질 때뿐 아니라 다음 effect 실행 직전에도 불린다.
        • 의존성은 Object.is 로 비교. 매 렌더 새로 만드는 객체·함수를 넣으면 매번 실행된다.
        더 알아보기: Effect 가 필요 없는 경우, 경쟁 상태
        • props/state 로 계산 가능한 값 → 렌더 중에 계산 (effect 로 맞추면 렌더가 2번)
        • 사용자 이벤트에 대한 반응 → 이벤트 핸들러에서
        • props 가 바뀔 때 state 초기화 → key 를 바꾸기

        경쟁 상태: 요청 A 를 보내고 바로 B 를 보냈는데 A 의 응답이 늦게 오면 오래된 데이터가 화면을 덮습니다. cleanup 에서 ignore = true 를 세우거나 AbortController 로 요청을 취소합니다.

        miniReact 에서는React 와 같은 순서로 동작합니다. useLayoutEffect 는 DOM 반영 직후 바로, useEffect 는 requestAnimationFrame 다음 작업으로 미뤄 화면을 그린 뒤에 실행합니다. 다음 업데이트 전이나 언마운트 전에는 밀린 useEffect 를 먼저 실행합니다. ⏳ Effect 타이밍 예제에서 순서와 깜빡임 차이를 직접 볼 수 있고, Phase 2 의 타이머는 의존성 배열과 cleanup(clearInterval) 예시입니다.

  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }

        과제 핵심
        Virtual DOM 이 실제 DOM 보다 빠른가요?
        아닙니다. 바꿀 곳을 정확히 알고 직접 고치는 게 가장 빠릅니다. Virtual DOM 은 비교 비용을 더 내는 대신, 개발자가 바꿀 곳을 관리하지 않아도 불필요한 DOM 조작과 Reflow 를 줄여 "충분히 빠르게" 해줍니다. 핵심 가치는 속도보다 선언적 개발입니다.
        실제 DOM 은 왜 느린가요?
        크기나 위치를 바꾸면 브라우저가 레이아웃을 다시 계산(Reflow)하고 다시 칠(Repaint)해야 하는데, 이게 연쇄적으로 번질 수 있어서입니다. 조작 한 번이 느리다기보다 불필요하게 자주 조작하는 게 문제입니다.
        Diff 알고리즘이 O(n³) 대신 O(n) 인 이유는?
        두 가지 가정 덕분입니다. ① 타입이 다르면 하위 비교 없이 교체한다. ② 형제 리스트는 key 로 같은 노드를 찾는다. 그리고 같은 레벨끼리만 비교합니다.
        최소 변경을 위한 5가지 케이스는?
        추가(INSERT), 삭제(REMOVE), 태그가 바뀌면 교체(REPLACE), 텍스트만 바뀌면 텍스트 수정(TEXT), 같은 태그에서 속성만 바뀌면 속성 수정(PROPS)입니다. 여기에 key 가 같은 노드의 이동(MOVE)을 더했습니다.
        key 에 index 를 쓰면 어떤 문제가 생기나요?
        항목이 추가·삭제·정렬되면 index 가 바뀌어 다른 항목으로 인식됩니다. DOM 변경이 늘고, 더 심각하게는 입력값 같은 상태가 엉뚱한 항목에 붙습니다. 고유한 id 를 써야 합니다.
        Hooks 는 어떻게 상태를 유지하나요?
        상태를 함수 밖, 컴포넌트 인스턴스의 저장소(배열 또는 연결 리스트)에 둡니다. 렌더링 전에 "지금 렌더링 중인 컴포넌트"를 등록하고 인덱스를 0 으로 맞춘 뒤, Hook 이 호출될 때마다 인덱스를 하나씩 올려 그 칸을 씁니다. 순서가 곧 식별자라서 조건문 안에서 부르면 안 됩니다.
        setState 는 상태 변경 말고 무엇을 하나요?
        같은 값이면 렌더링을 건너뛰고, 다르면 리렌더링을 예약합니다. 예약은 모아서 한 번에 처리(batching)되고, 그 결과 화면이 다시 그려지며 의존성이 바뀐 effect 가 다시 실행됩니다.
        setState 직후에 값을 읽으면 왜 이전 값인가요?
        setState 는 값을 즉시 바꾸지 않고 다음 렌더를 예약합니다. 지금 실행 중인 함수의 state 는 그 렌더 시점에 찍힌 스냅샷입니다. 이전 값을 기준으로 연속해서 바꾸려면 setN(prev => prev + 1) 을 씁니다.
        여러 상태 변경을 한 번에 처리하는 방법은?
        Batching 입니다. setState 마다 바로 그리지 않고 업데이트를 큐에 모은 뒤 한 번만 렌더링합니다. React 18 부터는 어디서든 자동입니다. miniReact 는 microtask 로 한 번만 예약하는 방식으로 구현했습니다.
        State 는 어디에 두는 게 좋나요?
        그 state 를 쓰는 모든 컴포넌트의 가장 가까운 공통 부모입니다(Lifting State Up). 계산으로 얻을 수 있는 값은 state 로 두지 않습니다.
        UI 를 컴포넌트로 어떻게 나눴나요?
        한 컴포넌트가 한 가지 역할만 하도록 나눴습니다. 스터디 플래너는 진행률(Header), 입력(TodoForm), 필터(Toolbar), 목록(TodoList)과 항목(TodoItem), 타이머, 배칭 데모로 나눴고, 상태는 루트 App 에만 두고 자식은 props 만 받는 순수 함수로 만들었습니다.
        useEffect 와 useLayoutEffect 의 차이는?
        useEffect 는 보통 화면을 그린 뒤 실행되어 화면 표시를 막지 않습니다. useLayoutEffect 는 그리기 전에 동기로 실행됩니다. 크기를 재서 위치를 정하는 등 깜빡임을 막을 때만 씁니다.
        useMemo, useCallback, React.memo 는 언제 쓰나요?
        useMemo 는 계산 결과를, useCallback 은 함수를, React.memo 는 렌더 결과를 기억합니다. 무거운 계산이나, memo 된 자식에게 넘기는 props 의 참조를 유지해야 할 때 씁니다. 측정한 뒤 필요한 곳에만 씁니다.
        Fiber 는 왜 도입됐나요?
        예전 재귀 방식은 한번 시작하면 멈출 수 없어 큰 트리를 비교하는 동안 화면이 끊겼습니다. Fiber 는 작업을 쪼개서 급한 일이 오면 멈추고 나중에 이어서 할 수 있게 했습니다. 동시성 렌더링과 Suspense 의 기반입니다.
        구현한 React 와 실제 React 의 가장 큰 차이는?
        ① 비교가 재귀라 중간에 못 멈춥니다(React 는 Fiber). ② 상태가 루트에만 있습니다. ③ 우선순위 없이 microtask 하나로 배칭합니다. ④ 이벤트를 루트 하나에 위임하지 않고 요소마다 붙입니다. ⑤ Suspense, 에러 경계, SSR 등이 없습니다. 반대로 리스트 이동은 LIS 로 React 보다 적게 움직입니다.
