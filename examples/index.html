각 예제 위의 망가뜨리기 버튼을 누르면 그 앱만 "잘못 짠 코드"로 다시 마운트됩니다. 같은 버튼을 한 번 더 누르면 복구돼요. 코드를 직접 고칠 필요가 없습니다.

📊 1,000행 리스트

성능useMemouseRef대량 key 리스트
이 예제에서 볼 것
  • 노드가 약 9,000개인 표에서 "한 명 점수 +1"을 누르면 DOM 변경은 단 몇 건입니다. 전체를 다시 그리지 않는다는 증거예요.
  • "점수 높은 순"으로 정렬한 상태에서 점수를 올리면 그 행이 위로 올라갑니다 (MOVE).
  • 검색하면 맞지 않는 행이 REMOVE 되고, 지우면 다시 INSERT 됩니다.
  • 렌더 + diff + patch 에 걸린 시간(ms)도 확인해 보세요.
  • 관계없는 리렌더: 화면에 안 쓰는 state 만 바꿔서 렌더링만 다시 일으킵니다. "필터·정렬 계산" 횟수가 그대로인 건 useMemo 덕분입니다.
⚖️ Virtual DOM vs 전체 다시 그리기

"한 명 점수 +1" 과 같은 변경을 두 방식으로 각각 5번씩 해서 비교합니다. 시간에는 브라우저 레이아웃 계산까지 포함됩니다.

⏱ 스톱워치

useEffectcleanupuseRefINSERT
이 예제에서 볼 것
  • useEffect(…, [running]): 시작하면 interval 을 등록하고, 정지하면 cleanup 에서 clearInterval 합니다.
  • 누적 시간은 화면과 무관한 값이라 useRef 에 둡니다. 바꿔도 리렌더링되지 않아요.
  • 초당 30번 넘게 렌더링되지만 매번 시간 텍스트 하나만 바뀝니다 (TEXT 1).
  • 랩을 누르면 맨 위에 새 행이 추가됩니다. 기존 행은 key 로 재사용 (INSERT 1).

⏳ Effect 타이밍

useEffectuseLayoutEffect브라우저 그리기
이 예제에서 볼 것
  • 데모 1: useLayoutEffect 는 DOM 반영 직후 그리기 전, useEffect 는 화면을 그린 뒤에 실행됩니다. 기록된 ①②③ 순서를 확인하세요.
  • 데모 2: 툴팁 위치를 재서 옮기는 코드입니다. useEffect 로 하면 잘못된 자리에 있는 툴팁이 잠깐 보였다가 옮겨집니다 (깜빡임).
  • useLayoutEffect 로 바꾸면 위치를 다 잡은 뒤에야 그리므로 잘못된 자리가 보이지 않습니다. 대신 측정하는 동안 화면이 잠깐 멈춥니다.
결론
  • 대부분은 useEffect. 사용자에게 중간 상태가 보이면 안 될 때만 useLayoutEffect.

🎨 Context vs Props Drilling

createContextuseContextProps Drilling
이 예제에서 볼 것
  • 왼쪽은 Page → Section → Card 가 쓰지도 않는 theme, user 를 계속 받아서 넘깁니다 (Props Drilling).
  • 오른쪽은 Provider 로 감싸 두고, 맨 아래에서 useContext 로 바로 꺼냅니다. 중간 컴포넌트는 아무것도 몰라요.
  • 화면 결과는 똑같습니다. 차이는 코드입니다. 전달할 값이 늘어나거나 단계가 깊어질수록 왼쪽은 고칠 곳이 많아집니다.
  • miniReact 의 useContext 는 상태를 만들지 않는 "읽기" 라서 자식 컴포넌트에서도 쓸 수 있게 했습니다.
