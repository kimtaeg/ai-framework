## 1. RESP 클라이언트 — 실제 Redis 와 말하는 법 (`experiment/resp.js`)

**하는 일:** 의존성 없이 TCP 소켓 하나로 실제 Redis 에 명령을 보내고 응답을 읽습니다.

**핵심:** Redis 프로토콜(RESP)은 "글자 수를 먼저 말하고 내용을 보내는" 형식입니다.

```
SET a 1  →  *3\r\n $3\r\nSET\r\n $1\r\na\r\n $1\r\n1\r\n
             └ 인자 3개   └ 3글자 "SET"   └ 1글자 "a"   └ 1글자 "1"
응답      →  +OK\r\n (성공) · $5\r\nhello\r\n (5글자 문자열) · $-1\r\n (없음 = null) · :1\r\n (정수)
```

**왜 이렇게:** 길이를 먼저 알려 주니까 받는 쪽이 "어디까지가 한 응답인지"를 문자열을 훑지 않고 바로 압니다. 그래서 파싱이 빠릅니다.
응답은 보낸 순서대로 오므로, 보낼 때 `queue` 에 `resolve` 를 넣고 응답이 오면 앞에서부터 꺼내 줍니다(파이프라이닝). 연결 하나로 요청 여러 개를 기다리지 않고 연달아 보낼 수 있습니다.

**미니 레디스와의 차이:** 미니 레디스는 HTTP + JSON 이라 요청마다 헤더(수백 바이트), URL 파싱, JSON 직렬화가 붙습니다. E3 에서 미니 레디스가 느린 가장 큰 이유입니다.

## 2. 히트율을 정확히 조절하는 법 (`experiment/k6/cache.js`)

**하는 일:** "히트율 90%" 를 말 그대로 90% 로 만듭니다.

```js
Math.random() < HIT
  ? http.get(url(rnd(HOT)))                         // 미리 데운 키 1,000개 중 하나 → HIT
  : http.get(url(rnd(ROWS), `&v=${vu}-${iter}`))    // 매번 새 캐시 키 → 반드시 MISS
```

**왜 이렇게:** 그냥 무작위 키를 고르면 히트율이 시간에 따라 계속 변합니다(캐시가 점점 차니까). MISS 가 나야 하는 요청에 **한 번도 쓴 적 없는 꼬리표(`v`)** 를 붙이면 캐시에 절대 없으므로 확실히 MISS 가 납니다.
MISS 는 진짜 MISS 처럼 동작합니다: 캐시 조회 → DB 쿼리 → 캐시 저장(SET)까지 다 합니다.
**설정값이 아니라 응답 헤더 `X-Cache` 로 실측한 히트율**을 같이 기록하고, 공식에는 실측값을 넣습니다.

## 3. Zipf 생성기 — 인기 키에 요청이 몰리는 분포 (`experiment/k6/cache.js`)

**하는 일:** YCSB 표준처럼 "상위 몇 개 키가 요청 대부분을 차지하는" 패턴을 만듭니다. θ=0.99 이면 순위 k 번째 키가 뽑힐 확률은 대략 1/k 에 비례합니다.

**핵심:** 10만 개에 대한 정규화 상수 `zetan = Σ 1/i^θ` 를 한 번 계산해 두고, 균등 난수 u 하나를 Gray 등의 공식으로 순위로 바꿉니다(YCSB `ZipfianGenerator` 와 같은 식). 그다음 FNV 해시로 순위를 섞어서, 인기 키가 id 1, 2, 3 에 몰리지 않고 테이블 전체에 흩어지게 합니다.

**왜 이렇게:** 실제 서비스는 균등하지 않습니다(인기 상품, 메인 페이지). 균등 분포로 재면 캐시 효과를 과소평가하게 됩니다. 업계 표준(YCSB)을 따르면 "내 마음대로 정한 패턴" 이라는 비판을 피할 수 있습니다.

## 4. 테이블을 정확히 10만 건으로 되돌리기 (`experiment/app.js`)

**하는 일:** 측정마다 상품 테이블을 처음 상태(10만 건)로 되돌립니다.

```js
await db.close();                 // 워커 스레드 종료 (밀려 있던 쿼리도 끊김)
truncateSync(TBL, BASE_BYTES);    // 파일을 처음 크기로 자름
db = createDbService(...);        // 워커가 파일을 다시 읽어 B+ 트리 재구성
```

**왜 필요했나:** YCSB A·B 의 쓰기가 INSERT 로 행을 계속 추가해서 테이블이 10만 → 34만 건으로 커졌고, 전체 읽기 쿼리가 점점 느려져 **나중 회차일수록 결과가 나빠지는 오염**이 생겼습니다. (같은 조건인데 2~4배 차이)

**왜 이 방법이 맞나:** 미니 DBMS 의 INSERT 는 **파일 끝에 한 줄씩 덧붙이기만** 합니다(append-only). 그래서 처음 크기만 기억해 두면 자르는 것만으로 정확히 되돌아갑니다. 되돌린 뒤 행 수를 다시 세어서 10만 건이 아니면 측정을 멈춥니다.

## 5. 두 공식이 왜 맞는가

**E1 응답시간 — 대기열이 없을 때 (VU 1명)**

```
T(h) = h × T_hit + (1 − h) × T_miss
```

요청이 한 번에 하나뿐이라 서로 기다리지 않습니다. 그러면 평균 응답시간은 HIT 시간과 MISS 시간의 **가중 평균**일 뿐입니다. T_hit 와 T_miss 는 히트율 100% · 0% 에서 따로 잰 값입니다.

**E2 처리량 — DB 가 병목일 때 (VU 50명)**

```
X(h) = min( X_db / (1 − h),  X_cache )
```

DB 는 1초에 X_db 건밖에 못 처리합니다(무거운 쿼리, 워커 2개). 전체 요청 중 DB 로 가는 몫은 (1 − h) 뿐이므로, DB 가 꽉 찰 때 전체 처리량은 X_db ÷ (1 − h) 입니다.
히트율 90% → DB 몫 1/10 → 처리량 10배. 99% → 100배. 다만 캐시 쪽 한계(X_cache, 히트율 100% 에서 잰 값)를 넘을 수는 없습니다.

**의미:** 공식이 실측과 맞으면, 다른 사람도 **자기 DB 의 처리량과 히트율만 알면** 캐시 이득을 계산할 수 있습니다. 컴퓨터마다 다른 절대 숫자 대신 공식이 "모두에게 같은 결과" 입니다.

## 7. 최적화 두 가지 — "무엇을 바꿨고, 결과가 같은 건 어떻게 아나요?" 대비

### 7-1. 미니 레디스 호출을 가볍게 (`week2/redis/node-fetch.js`)

**찾은 방법:** 미니 레디스가 히트율 100% 에서도 손해(0.92배)라서 `node --cpu-prof` 로 API 서버를 프로파일했습니다. 저장소(미니 레디스 서버)는 CPU 28% 로 놀고 있었고, API 서버 CPU 의 상당 부분이 Node 내장 `fetch`(undici) 의 웹 표준 처리(스트림, Headers 객체)에 쓰였습니다.

**바꾼 것:** `MiniRedisClient` 는 원래 `{ fetch }` 를 바꿔 끼울 수 있게 되어 있습니다. 상태 코드와 JSON 본문만 돌려주는 작은 함수를 `node:http` + keep-alive 로 만들어 넣었습니다.

```js
const agent = new http.Agent({ keepAlive: true });   // 연결을 매번 새로 만들지 않고 재사용
http.request(url, { method, headers, agent }, (res) => { ... resolve({ status, json: async () => JSON.parse(text) }) });
```

**결과:** 요청 하나에 드는 API 서버 CPU 0.27ms → 0.10ms, 히트율 100% 0.92배 → 1.48배. HTTP + JSON 이라는 방식은 그대로입니다.

### 7-2. 전체 읽기에서 조건 열만 먼저 보기 (`week2/dbms/engine.js` · `storage.js`)

**바꾼 것:** `WHERE name = '키보드 5'` 는 10만 줄을 다 읽지만 맞는 줄은 1개뿐입니다. 예전에는 줄마다 4개 열을 모두 해석(디코딩·형 변환)한 뒤 조건을 봤습니다. 이제는 쉼표 위치만 찾아 **조건 열 하나만** 꺼내 보고(`decodeField`), 맞는 줄만 전체를 해석합니다.

```js
for (const c of conds) if (!test(typedValue(decodeField(line, c.i), c.i, numeric), c.op, c.value)) return; // 대부분 여기서 탈락
const raw = decodeRow(line);   // 맞는 줄만
```

**왜 결과가 같나:** 따옴표가 없는 줄은 해석 중에 오류가 날 수 없어서 일부만 봐도 됩니다. 따옴표가 있는 줄은 예전처럼 처음부터 전체를 해석합니다 (형식 오류를 놓치지 않게). 그리고 이전 코드와 새 코드에 무작위 줄 25만 개 · 무작위 SELECT 8,000개를 넣어 **결과와 에러가 완전히 같은지** 대조했습니다.

**결과:** 전체 읽기 82ms → 27ms (3배), DB 처리량 22.8 → 68.8 req/s. 처리량 공식 $X_{db} \div (1 - h)$ 는 DB 가 빨라진 뒤에도 그대로 맞았습니다.

## 8. 확장 실험 세 가지 — 통신 방식 · 네트워크 지연 · 요청당 CPU

### 8-1. 미니 레디스 RESP/TCP 모드 (`experiment/resp.js` 의 `startRespServer` · `experiment/miniredis-server.js`)

**하는 일:** 미니 레디스 프로세스 하나가 포트 두 개로 말합니다. `:6380` 은 원래의 HTTP + JSON, `:6381` 은 실제 Redis 와 같은 RESP. **두 포트가 같은 저장소(같은 해시 테이블)를 씁니다.** 그래서 `mini` 와 `miniresp` 의 차이는 오직 "말하는 방식" 입니다.

```js
const handler = (args) => s.redis.command(args);          // 저장소 코드는 한 줄도 안 바꿈
await startRespServer({ handler, port: 6381 });
// 서버: 한 번에 도착한 명령들(파이프라이닝)을 순서대로 실행하고, 응답을 모아 한 번에 쓴다
for (;;) { const r = parseRequest(buf, off); if (!r) break; out += encodeReply(handler(r.args), name); }
sock.write(out);
```

**왜:** "미니 레디스가 Redis 보다 느린 건 저장소 때문인가, HTTP + JSON 때문인가?" 를 가르려면 저장소는 그대로 두고 통신만 바꿔야 합니다. `+OK` 같은 상태 응답과 `$2\r\nOK` 같은 값 응답을 구분하는 것까지 Redis 와 같게 했고, 무작위 명령을 RESP 서버를 거쳐 실행한 결과와 저장소에 직접 실행한 결과가 같은지(조각난 바이트 · 잘못된 요청 포함) 테스트로 대조합니다.

### 8-2. 네트워크 지연 주입 (`experiment/netem.js`)

**하는 일:** 리눅스 `tc netem` 으로 **앱 컨테이너에서 캐시 컨테이너로 나가는 패킷만** 1ms(± 0.2ms) 늦춥니다.

```sh
tc qdisc add dev eth0 root handle 1: prio bands 3 priomap 2 2 2 …   # 기본은 지연 없는 칸
tc qdisc add dev eth0 parent 1:1 handle 10: netem delay 1000us 200us distribution normal
tc qdisc add dev eth0 parent 10:1 pfifo limit 10000                  # 지터가 있어도 패킷 순서 유지
tc filter add dev eth0 parent 1: protocol ip u32 match ip dst <캐시 IP>/32 flowid 1:1
```

**왜 이렇게:**
- **나가는 쪽에만** 걸면 요청 하나가 그 구간을 한 번 지나므로 왕복이 정확히 +1ms 입니다 (측정: Redis PING 0.06ms → 1.2ms).
- **목적지 필터**로 k6 → 앱 구간은 건드리지 않습니다. 그래서 "캐시 없음" 은 지연 조건에서도 같아야 하고, 이게 대조군 역할을 합니다.
- 지터가 있으면 netem 이 패킷 순서를 바꿔 TCP 재전송이 생길 수 있어서, 안쪽 큐를 `pfifo` 로 바꿨습니다 (netem 공식 문서의 방법).
- **한계:** 미니 DBMS 는 앱 서버 안(워커 스레드)에 있어서 DB 구간에는 네트워크가 없습니다. 즉 지연이 캐시에만 붙는, **캐시에 가장 불리한 경우**입니다. 실제 클라우드에서는 DB 도 원격이라 MISS 가 더 비쌉니다.

### 8-3. 요청당 CPU 측정 (`experiment/k6/cache.js` 의 `cpuMark` · `experiment/app.js` 의 `/admin/cpu`)

**하는 일:** k6 가 측정 시작 순간과 끝 순간에 `/admin/cpu` 를 한 번씩 부릅니다. 앱 서버는 자기 프로세스의 누적 CPU 시간(`process.cpuUsage()`, 워커 스레드 포함), 미니 레디스의 누적 CPU(RESP 실험용 명령 `XCPU`), Redis 의 누적 CPU(`INFO cpu`)를 돌려줍니다. 두 값의 차이 ÷ 그 구간의 요청 수 = **요청 하나당 CPU 시간(ms)** 입니다.

**왜:** 처리량만 보면 "느리다" 는 것만 알지 어디서 느린지 모릅니다. 요청당 CPU 를 부르는 쪽(앱 서버)과 응답하는 쪽(캐시 서버)으로 나누면, HTTP + JSON 비용이 어느 쪽에서 드는지 숫자로 보입니다. 워밍업 · 캐시 데우기 구간은 빠지도록 측정 구간의 시작 · 끝에서만 잽니다.
