## 1. RESP 클라이언트 — 실제 Redis 와 말하는 법 (`experiment/resp.js`)

**하는 일:** 의존성 없이 TCP 소켓 하나로 실제 Redis 에 명령을 보내고 응답을 읽습니다.

**핵심:** Redis 프로토콜(RESP)은 "글자 수를 먼저 말하고 내용을 보내는" 형식입니다.

```
SET a 1  →  *3\r\n $3\r\nSET\r\n $1\r\na\r\n $1\r\n1\r\n
             └ 인자 3개   └ 3글자 "SET"   └ 1글자 "a"   └ 1글자 "1"
응답      →  +OK\r\n (성공) · $5\r\nhello\r\n (5글자 문자열) · $-1\r\n (없음 = null) · :1\r\n (정수)
```

**왜 이렇게:** 길이를 먼저 알려 주니까 받는 쪽이 "어디까지가 한 응답인지"를 문자열을 훑지 않고 바로 압니다. 그래서 파싱이 빠릅니다.
응답은 보낸 순서대로 오므로, 보낼 때 `queue` 에 `resolve` 를 넣고 응답이 오면 앞에서부터 꺼내 줍니다(파이프라이닝). 연결 하나로 요청 여러 개를 기다리지 않고 연달아 보낼 수 있습니다.

**미니 레디스와의 차이:** 미니 레디스는 HTTP + JSON 이라 요청마다 헤더(수백 바이트), URL 파싱, JSON 직렬화가 붙습니다. E3 에서 미니 레디스가 느린 가장 큰 이유입니다.

## 2. 히트율을 정확히 조절하는 법 (`experiment/k6/cache.js`)

**하는 일:** "히트율 90%" 를 말 그대로 90% 로 만듭니다.

```js
Math.random() < HIT
  ? http.get(url(rnd(HOT)))                         // 미리 데운 키 1,000개 중 하나 → HIT
  : http.get(url(rnd(ROWS), `&v=${vu}-${iter}`))    // 매번 새 캐시 키 → 반드시 MISS
```

**왜 이렇게:** 그냥 무작위 키를 고르면 히트율이 시간에 따라 계속 변합니다(캐시가 점점 차니까). MISS 가 나야 하는 요청에 **한 번도 쓴 적 없는 꼬리표(`v`)** 를 붙이면 캐시에 절대 없으므로 확실히 MISS 가 납니다.
MISS 는 진짜 MISS 처럼 동작합니다: 캐시 조회 → DB 쿼리 → 캐시 저장(SET)까지 다 합니다.
**설정값이 아니라 응답 헤더 `X-Cache` 로 실측한 히트율**을 같이 기록하고, 공식에는 실측값을 넣습니다.

## 3. Zipf 생성기 — 인기 키에 요청이 몰리는 분포 (`experiment/k6/cache.js`)

**하는 일:** YCSB 표준처럼 "상위 몇 개 키가 요청 대부분을 차지하는" 패턴을 만듭니다. θ=0.99 이면 순위 k 번째 키가 뽑힐 확률은 대략 1/k 에 비례합니다.

**핵심:** 10만 개에 대한 정규화 상수 `zetan = Σ 1/i^θ` 를 한 번 계산해 두고, 균등 난수 u 하나를 Gray 등의 공식으로 순위로 바꿉니다(YCSB `ZipfianGenerator` 와 같은 식). 그다음 FNV 해시로 순위를 섞어서, 인기 키가 id 1, 2, 3 에 몰리지 않고 테이블 전체에 흩어지게 합니다.

**왜 이렇게:** 실제 서비스는 균등하지 않습니다(인기 상품, 메인 페이지). 균등 분포로 재면 캐시 효과를 과소평가하게 됩니다. 업계 표준(YCSB)을 따르면 "내 마음대로 정한 패턴" 이라는 비판을 피할 수 있습니다.

## 4. 테이블을 정확히 10만 건으로 되돌리기 (`experiment/app.js`)

**하는 일:** 측정마다 상품 테이블을 처음 상태(10만 건)로 되돌립니다.

```js
await db.close();                 // 워커 스레드 종료 (밀려 있던 쿼리도 끊김)
truncateSync(TBL, BASE_BYTES);    // 파일을 처음 크기로 자름
db = createDbService(...);        // 워커가 파일을 다시 읽어 B+ 트리 재구성
```

**왜 필요했나:** YCSB A·B 의 쓰기가 INSERT 로 행을 계속 추가해서 테이블이 10만 → 34만 건으로 커졌고, 전체 읽기 쿼리가 점점 느려져 **나중 회차일수록 결과가 나빠지는 오염**이 생겼습니다. (같은 조건인데 2~4배 차이)

**왜 이 방법이 맞나:** 미니 DBMS 의 INSERT 는 **파일 끝에 한 줄씩 덧붙이기만** 합니다(append-only). 그래서 처음 크기만 기억해 두면 자르는 것만으로 정확히 되돌아갑니다. 되돌린 뒤 행 수를 다시 세어서 10만 건이 아니면 측정을 멈춥니다.

## 5. 두 공식이 왜 맞는가

**E1 응답시간 — 대기열이 없을 때 (VU 1명)**

```
T(h) = h × T_hit + (1 − h) × T_miss
```

요청이 한 번에 하나뿐이라 서로 기다리지 않습니다. 그러면 평균 응답시간은 HIT 시간과 MISS 시간의 **가중 평균**일 뿐입니다. T_hit 와 T_miss 는 히트율 100% · 0% 에서 따로 잰 값입니다.

**E2 처리량 — DB 가 병목일 때 (VU 50명)**

```
X(h) = min( X_db / (1 − h),  X_cache )
```

DB 는 1초에 X_db 건밖에 못 처리합니다(무거운 쿼리, 워커 2개). 전체 요청 중 DB 로 가는 몫은 (1 − h) 뿐이므로, DB 가 꽉 찰 때 전체 처리량은 X_db ÷ (1 − h) 입니다.
히트율 90% → DB 몫 1/10 → 처리량 10배. 99% → 100배. 다만 캐시 쪽 한계(X_cache, 히트율 100% 에서 잰 값)를 넘을 수는 없습니다.

**의미:** 공식이 실측과 맞으면, 다른 사람도 **자기 DB 의 처리량과 히트율만 알면** 캐시 이득을 계산할 수 있습니다. 컴퓨터마다 다른 절대 숫자 대신 공식이 "모두에게 같은 결과" 입니다.
