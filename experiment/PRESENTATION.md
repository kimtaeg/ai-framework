## [2:00 ~ 3:30] 결과 — 하이라이트

[화면: ④ 맨 위 결과 표 세 줄]

결론은 세 가지입니다.

[화면: E2 그래프 → 아래 표의 90%, 95% 줄]

첫째, 무거운 쿼리에서는 처리량이 공식대로 늘어납니다. DB로 가는 몫이 1 빼기 히트율이니까, 히트율 90%면 10배입니다. 실측이 9.1배, 9.6배로, 90%까지 공식과 오차 9% 이내였습니다. ★ 95%를 넘으면 드물게 오는 MISS가 사용자를 오래 붙잡아서 공식보다 낮게 나옵니다.

[화면: "이 공식이 모두에게 같은 결과입니다" 줄]

이게 중요한 이유는, 컴퓨터마다 절대 숫자는 달라도 이 공식은 같기 때문입니다. 여러분 DB의 처리량과 히트율만 알면 이득을 계산할 수 있습니다.

[화면: E3 표 → "최적화 전" 줄의 0.92배]

둘째, 가벼운 쿼리에서는 캐시가 손해일 수 있습니다. 처음 쟀을 때 저희 미니 레디스는 히트율 100%여도 캐시가 없을 때보다 느렸습니다. 0.92배였습니다.

[화면: CPU 표 → "28%", "0.27ms"]

원인을 찾으려고 CPU를 봤더니, 미니 레디스 서버는 28%밖에 안 썼습니다. 느린 건 저장소가 아니라, API 서버가 캐시를 부를 때마다 HTTP 요청을 만드는 비용이었습니다. 프로파일러로 보니 Node 내장 fetch가 무거웠습니다.

[화면: "최적화 후" 줄의 1.48배, CPU 표의 "0.10ms"]

그래서 같은 HTTP와 JSON을 쓰되 가벼운 요청 방식으로 바꿨습니다. 요청 하나에 드는 CPU가 2.8배 줄었고, 0.92배가 1.48배로 바뀌었습니다. 그래도 히트율이 64%보다 낮으면 여전히 손해입니다. 캐시를 부르는 비용이 손익을 가른다는 겁니다.

[화면: ④ 맨 위 표 3번 줄]

★ 셋째, 쓰기가 늘수록 이득이 사라집니다. 읽기만 할 때 1.63배였던 Redis가, 쓰기가 절반이 되자 1.00배가 됐습니다.

# QnA 대비 — 20초 답변

답변 구조: **결론(5초) → 근거·수치(10초) → 한계 인정(5초)**

### Q1. 왜 직접 만든 미니 레디스 말고 실제 Redis 를 비교 대상으로 넣었나요? 불공평하지 않나요? (트레이드오프)

> 기준점이 필요해서 넣었습니다. 같은 조건에서 실제 Redis 가 3.95배 나왔으니, 미니 레디스의 0.92배가 "캐시라는 방법" 의 문제가 아니라 "저희 구현" 의 문제라는 게 드러났고, 원인(HTTP 호출 비용)을 고쳐 1.48배로 올렸습니다. 다만 지금도 요청당 비용이 Redis 의 2.4배이고, 프로토콜까지 다르니 엔진만의 비교는 아니라는 점은 인정합니다.

### Q2. 노트북 한 대에서 잰 건데, 이 숫자가 의미가 있나요? (한계)

> 절대 숫자는 의미가 제한적이라 공식으로 일반화했습니다. 히트율 90% 까지 공식과 실측 오차가 9% 이내였고, 최적화로 DB 가 3배 빨라진 뒤에도 같은 공식을 따랐습니다. 이 공식은 DB 처리량과 히트율만 넣으면 어느 환경에서나 계산됩니다. 다만 다른 컴퓨터에서 같은 배율이 나오는지는 아직 확인하지 못해서, 팀원 노트북으로 재현하는 게 다음 과제입니다.

### Q3. 실제 서비스처럼 트래픽이 많거나 서버가 여러 대면 어떻게 되나요? (확장성)

> 서버가 여러 대면 Redis 같은 외부 캐시가 더 유리해집니다. 지난주 실험에서 서버 안 Map 이 미니 레디스보다 3.9배 빨랐지만, 서버끼리 캐시를 공유하지 못하고 재시작하면 비워집니다. 반대로 네트워크 지연이 생기면 캐시 왕복 비용이 커져서, 가벼운 쿼리에서는 손해가 더 커질 겁니다. 그 손익분기를 지연을 넣어서 다시 재 보려고 합니다.
