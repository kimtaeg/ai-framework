## [0:00 ~ 0:25] 도입 — 결론부터 & 10.7배의 착시

[화면: ① 표 "우리가 만든 것"]

안녕하세요. 오늘은 직접 만든 **미니 레디스**와 **미니 DBMS**, 그리고 **Redis 7**을 비교하며 **"캐시는 언제 이득이고 언제 손해인가"**를 576회 실측한 결과를 발표하겠습니다.

[화면: 416 req/s 계산 표]

처음엔 캐시를 붙이니 **10.7배** 빨랐습니다. 그런데 뜯어보니 원본 DB가 진짜 쿼리가 아니라 `120ms sleep`이었습니다. 50명이 기다리면 이론 상한이 416인데 실측이 401이었죠. **캐시가 아니라 sleep이 만든 숫자**였습니다. 그래서 진짜 DB 엔진 앞에서 다시 쟀습니다.

## [0:25 ~ 1:05] 실험 구조와 통제

[화면: ② 첫 번째 다이어그램]

k6가 요청을 보내면 API 서버가 캐시를 먼저 보고, 없으면 미니 DBMS를 조회합니다. 캐시는 **없음 · 미니 레디스 HTTP · 미니 레디스 RESP · Redis 7** 네 가지를 바꿔 끼웠고, 모두 Docker에서 CPU 코어를 격리해 **96개 조건 × 6회, 총 576회** 쟀습니다.

[화면: ③ "측정 중 발생한 오염과 해결" 표]

오염을 막기 위해 히트율은 응답 헤더로 실측했고, 반복마다 순서를 섞었으며, 쓰기 테스트로 커진 테이블은 매 회차 `truncate`로 **정확히 10만 건**을 유지했습니다.

## [1:05 ~ 3:00] 핵심 결과 세 가지

[화면: ④ 맨 위 결과 표]

핵심 세 가지만 말씀드리겠습니다.

[화면: 발견 1의 E2 그래프 → 표의 90% 줄]

**첫째, 무거운 쿼리는 공식대로 늡니다.**
DB로 가는 비율이 `(1 - 히트율)`이므로 처리량은 `DB 처리량 ÷ (1 - 히트율)`을 따릅니다. 실제 히트율 **90%까지 공식과 오차 ±7% 이내**였습니다. 내 DB 처리량과 히트율만 알면 캐시 효과는 미리 계산됩니다.

[화면: 발견 2의 E3 표 → 요청당 CPU 표]

**둘째, 가벼운 쿼리에서 미니 레디스가 느렸던 진짜 범인은 HTTP + JSON이었습니다.**
B+트리 단건 조회에선 히트율 100%여도 미니 레디스 HTTP가 **1.39배**, Redis 7이 **3.63배**였습니다.
그래서 **저장소는 그대로 두고 통신만 RESP로 바꿨더니 3.97배**로 뛰었고, 요청당 CPU도 **0.202ms에서 0.073ms로 Redis 7과 똑같아졌습니다.** 느린 건 JS 저장소가 아니라 HTTP와 JSON 변환 비용이었습니다.

[화면: 발견 3의 E6 그래프 → ④ 맨 위 결과 표의 3번째 줄]

**셋째, 캐시까지 왕복 1ms 지연이 생기면 대기열 유무로 갈립니다.**
동시 요청 50개일 땐 처리량이 **4~21%만 줄었지만**, 요청이 하나씩 올 땐 **DB 조회가 0.36ms인데 캐시 왕복이 1.2ms**라 히트율 100%여도 **오히려 3.9배 느렸습니다.** 원본 쿼리가 네트워크 왕복보다 싸면 캐시는 손해입니다.

[화면: 발견 3 아래 E7 한 줄]

다만 이건 캐시만 멀리 있는, 캐시에 가장 불리한 조건입니다. DB도 1ms 멀리 두면, 히트율 95%를 넘을 때 약 10% 이득이었습니다.

## [3:00 ~ 3:40] 신뢰도와 마무리

[화면: "이 측정값을 신뢰할 수 있는 객관적 근거" 표]

576회 중 **576회 모두 성공**했고, **97.6%**가 중앙값 ±15% 안에 들어왔습니다.

정리하겠습니다. 캐시는 무조건 빠른 게 아니라, **① 공식으로 예측 가능하고 ② HTTP·JSON 같은 통신비와 네트워크 왕복이 원본 쿼리보다 비싸면 오히려 손해**라는 점을 실측으로 확인했습니다. 이상으로 발표를 마치겠습니다. 감사합니다.
