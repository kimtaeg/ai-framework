[화면: 발견 1의 E2 그래프 → 아래 안내 두 줄]

[화면: 발견 2의 E3 표 → 손익분기 열]

**둘째, 가벼운 쿼리는 캐시가 이기기 어렵습니다.** 캐시 없이도 초당 **13,700건**이라, Redis도 히트율 **88%**는 넘어야 이득이고, 미니 레디스 HTTP는 **100%여도 손해**였습니다.

[화면: 요청당 CPU 표]

미니 레디스가 느린 원인은 저장소가 아니라 **HTTP와 JSON**이었습니다. 통신만 RESP로 바꾸자 초당 **6,800건이 19,000건**이 됐고, 요청당 CPU도 Redis와 같아졌습니다.

[화면: E4 표 → Redis 줄]

쓰기가 섞이면 더 불리합니다. 쓸 때마다 캐시를 지우기 때문에, Redis는 읽기만 할 때 **1배**에서 쓰기가 절반이면 **0.75배**로 떨어졌습니다.

[화면: 발견 3의 E5 표 → 감소 열]

**셋째, 캐시까지 왕복 1밀리초가 생기면,** 동시 요청이 50개일 땐 처리량이 **8~22%**만 줄었습니다.

[화면: E6 그래프 → 아래 E7 한 줄]

하지만 요청이 하나씩 오면 **0.39밀리초** DB 조회보다 캐시 왕복이 비싸서, 히트율 100%여도 **3.8배 느렸습니다.** DB도 같이 멀리 두면 히트율 **96%**를 넘어야 **6%** 정도 이득입니다.
