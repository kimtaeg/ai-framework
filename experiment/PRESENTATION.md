# QnA 대비 — 20초 답변

답변 구조: **결론(5초) → 근거·수치(10초) → 한계 인정(5초)**

### Q1. 실제 Redis 를 비교 대상으로 넣은 이유는? 불공평하지 않나요? (트레이드오프)

> 기준점이 필요해서 넣었습니다. Redis 가 3.63배인데 미니 레디스가 1.39배라서 원인을 찾았고, 저장소는 그대로 두고 통신만 RESP 로 바꾸자 3.97배로 같아졌습니다. 요청당 CPU 도 0.073ms 로 같습니다. 다만 캐시 서버 쪽만 보면 Redis 가 0.018ms, 저희가 0.023ms 로 Redis 가 1.3배 효율적이고, 병목이 API 서버라서 처리량에 안 드러났을 뿐이라는 점은 인정합니다.

### Q2. 노트북 한 대에서 잰 건데, 이 숫자가 의미가 있나요? (한계)

> 절대 숫자는 의미가 제한적이라 공식으로 일반화했습니다. 히트율 90% 까지 공식과 오차 7% 이내였고, 이 공식은 DB 처리량과 히트율만 넣으면 어느 환경에서나 계산됩니다. 다만 측정 중에 노트북 전원 정책 때문에 14분 동안 3% 느려진 구간도 있었고, 다른 컴퓨터에서 같은 배율이 나오는지는 아직 확인하지 못했습니다.

### Q3. 실제 서비스처럼 서버가 여러 대면 어떻게 되나요? (확장성)

> 캐시가 다른 서버에 있는 상황을 1ms 지연으로 만들어 봤습니다. 동시 요청이 많으면 처리량은 4~21% 만 줄었지만, 요청 하나의 응답시간은 히트율 100% 여도 캐시 없을 때보다 느렸습니다. 다만 저희 DB 는 API 서버 안에 있어서 DB 쪽 지연은 없었습니다. 실제로는 DB 도 원격이라 캐시가 더 유리할 것이고, DB 를 분리해서 다시 재는 게 다음 과제입니다.
